# 重构评估 · 单文件拆分

最后更新：v116（2026-11-18，按「AI 增删改效率」重评）

> **结论`写在最前面`**`：不要做「拆页面」式重构——这个项目没有页面可拆。
> 要做的是「分段抽取」：`**`CSS 先外移（推荐立刻做）→ JS 分文`件（看还需不需要大改）→ ES 模块化（不建议）**。
>
> **2026-11-18 按「让 AI 增删改更快」重评过一遍**（第 8 节）：阶段 0 从「CSS 外移」
> 扩成「换行统一 → CSS 外移去重 → 改动地图」三步，**JS 分文件降级为「暂不做」**。
>
> 本文是评估记录，不是待办清单。真要动手前先读完第 3 节的成本。

## 1. 实测规模（v115 重测）

| 部分                  | 行数         | 占比   |
| ------------------- | ---------- | ---- |
| JS（一个 `<script>` 块） | 约 14,330   | 77%  |
| CSS（六个 `<style>` 块） | 约 4,065    | 22%  |
| HTML 骨架             | 约 66       | 0.4% |
| 合计                  | **18,509** |      |

其他计数：**486 个具名函数**、**185 个 `ACTIONS` 键**、**23 个后端接口**、132 处顶层 `const` / `let`。

对照 v103：17,772 行 / 13,851 JS / 3,808 CSS / 182 键。需求 v104–v115 做满十二个版本后  
JS 涨约 480 行、CSS 涨约 260 行，**全是新增页面区块**（清债六子页、体重体脂、习惯月概览），  
没有一处是被迫塞进来的边角料。

**第一个结论**：这个文件不是「一个 HTML 页面」，而是一个 13.8k 行的 JS 应用，HTML 只有 66 行骨架，  
其余界面全靠 JS 拼字符串。所以「拆页面」这个说法本身不成立。

## 2. 三个真实的结构问题

### 2.1 CSS 按「版本」分层，不按「模块」

六个 `<style>` 块依次是：

| 块                 | 量级        | 来历              |
| ----------------- | --------- | --------------- |
| 无 id（基础层）         | 约 790 行   | 最早的一版 + 后来补的基础类 |
| `id="visual-v2"`  | 约 1,600 行 | v2 视觉重构         |
| `id="skins"`      | 约 405 行   | 皮肤变量层           |
| `id="new-pages"`  | 约 440 行   | 清债 / 体重等新页面     |
| `id="layout-v3"`  | 约 345 行   | 布局第三版           |
| `id="notify-v33"` | 约 495 行   | 通知 / 命令面板       |

后一版覆盖前一版，**生效完全依赖源码顺序**。全站有 **306 个选择器被重复定义**（v103 时 166，  
十二个版本翻了近一倍），最多的 `.sidebar` 已被定义 9 次、`.brand` 7 次。改样式时如果只改到  
前面那一份，现象就是「改了没反应」——这是本文件里唯一一条随版本**加速恶化**的指标。

这是目前**最大的结构性债务**，比「文件大」严重得多。

### 2.2 JS 是一个单作用域

486 个具名函数直接互调，没有任何 import / export。最大的几个是 `viewStats`（约 290 行）、  
`goView`（约 270 行）、`viewToday`（约 195 行）、`mergeStates`（约 190 行）、`habitCard`（约 185 行）。

好处是改起来不用管依赖图；坏处是无法判断「动这个函数会影响谁」。

### 2.3 `ACTIONS` 是一张横切表

`ACTIONS` 约 1,300 行、**185 个键**，所有模块的点击入口都平铺在里面：习惯、待办、清债、用药混在一起。

**这条决定了「按页面拆文件」拆不干净**——模块自己的渲染函数在各自文件里，  
但它的入口在中央大表里。要么把 `ACTIONS` 也按模块切成多个对象再合并，要么保留单一表。

## 3. 拆的真实成本（具体到工具，不是空谈）

| 影响面                    | 说明                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------- |
| `_check_script.mjs`    | 只解析**内联** `<script>`，带 `src` 的直接跳过。JS 外置后它读不到 `ACTIONS`，「data-act 漏 handler」这项检查会变成假绿 |
| `check-doc-anchors.py` | 它去 index.html 里找函数名和类名，符号搬走后锚点全报错。**只校验「文档提到、代码里没有」**，反向不查                            |
| SW 缓存清单                | `ASSETS` 要列全，漏一个就白屏，且只在二次访问 / 断网时暴露                                                   |
| 部署                     | 从「一个文件」变「十几个文件」，漏传过一次已删除的 `skin-cloud.css`，三套主题全没样式                                       |
| **样式顺序**               | 主题 CSS 的 `<link>` 在当前六个 `<style>` 块**之后**加载。外移的 CSS 必须插在主题链接之前，否则内联样式反压主题——最容易悄悄搞坏的一处 |

## 4. 分三阶段

### 阶段 0 · CSS 抽取（推荐，先做这个）

把 3,808 行 CSS 挪到一个外部文件，`<link>` 位置**放在主题那几个 link 之前**。

分两小步，别一步到位：

1. **原样外移**：一行内容都不改，只换位置。可逐字节比对，零逻辑风险。
2. **去重合并**：把 166 个重复选择器合成一条，保留最后生效的那份值。这一步有真实回归风险。

**验收**：三套对比度审计（页面 / 弹窗 / 命令卡）0 不达标 0 跳过 + 明暗两态各截一张图对比（v135 起只有一套主题）。

### 阶段 1 · JS 分文件（看还需不需要大改）

**用普通 script 串联，不引入模块系统**：

```html
<script src="js/core.js"></script>
<script src="js/sync.js"></script>
<script src="js/habits.js"></script>
```

因为仍在同一全局作用域，476 个函数互调**一行都不用改**。这是本项目唯一合适的拆法。

建议切成 8–10 个、每个 800–2,000 行，大致按：核心工具 / 云同步与合并 / 习惯 / 待办 / 清债 /  
用药 / 统计 / 日历与体重随笔 / 导航与启动。

**硬性规则：只搬位置，不改一行逻辑。** 每搬一块跑一遍全量回归。

前提是先补齐 `_check_script.mjs`（改成能读外链文件并汇总所有块里的 `ACTIONS`）。

### 阶段 2 · ES 模块化（不建议）

收益是真正的封装与依赖可见，成本是 476 个函数重新梳理 import / export，  
并且彻底破坏「无构建」的简单性（本地双击 HTML 就能跑这一点也会失去）。

除非哪天要多人长期协作，否则不值。

## 6. 明确不要做的事

1. **不要引入构建工具**（webpack / vite / rollup）。这个项目的价值之一就是「传上去就能跑」。
2. **不要为了「看起来整洁」整体重写**。13.8k 行里每一处奇怪写法背后基本都有一次事故。
3. **不要在拆分的同时改逻辑**。搬位置和改行为必须分成两个提交，否则出问题无法定位。
4. **不要按「页面」切分 JS**。见 2.3，`ACTIONS` 是横切的，按页面切必然留下跨文件调用。

## 8. v115 重评：目标是「让 AI 增删改更快」

第 1–7 节是按「人类长期可维护」排的。目标换成「改代码更快」之后，权重变了：
**排第一的不是 CSS，是换行。**

### 8.1 实测：工具摩擦比「找不到代码」更贵

| 文件 | CRLF | 裸 LF | 状态 |
| --- | --- | --- | --- |
| `index.html` | 18,372 | 137 | **混** |
| `api.php` | 825 | 0 | CRLF |
| `api/*.php` | 0 | 全部 | LF |
| `e2e/test-ics.php` / `test-backup.php` | 有 | 0 | CRLF |
| `e2e/test-schedule.php` / `test-push*.php` | 0 | 全部 | LF |
| `e2e/audit-contrast-v33.py` / `verify-batch3.py` | 有 | 有 | **混** |

仓库没有 `.gitattributes`，`core.autocrlf=false`，所以这些差异会原样进 diff。

后果：改一处要先判断这个文件的换行，猜错就是「字符串不匹配」整段重写。
v110–v115 六轮里，这类失败重写 4–5 次，占掉约两成操作时间——**比「函数在哪」更贵**。

### 8.2 重排后的优先级

| 优先级 | 动作 | 成本 | 对「改得快」的收益 | 原文档有吗 |
| --- | --- | --- | --- | --- |
| P0 | 换行统一（全 CRLF 或全 LF）+ `.gitattributes` | 30 分钟 | 高：Edit 一次过的概率接近 100% | 没有 |
| P0 | CSS 外移 + 去重（306 → 0） | 半天 | 高：改样式 1 处 vs 5–9 处 | 有（阶段 0） |
| P1 | 改动地图（功能 → 函数 / 三处同步点 / 对应测试） | 1 小时 | 高：省掉每次的探索性 grep | 没有 |
| P2 | JS 分文件 | 1–2 天 | 中：只省上下文，不省搜索 | 有（阶段 1） |
| 不做 | ESM / 构建工具 / 按页面切 | — | — | 有 |

### 8.3 两个结论变了

1. **CSS 不再是唯一的第一名，但仍是必做**。306 个重复选择器是「改了没反应」的根，
   AI 改样式同样会踩——而且踩了之后要重读好几处才能确认哪份生效。
2. **JS 分文件降级为「暂不做」**。它对「增删改」的贡献只有上下文读取，
   搜索范围一分没小；成本（部署 12 个文件、SW 清单漏一个就白屏、`_check_script.mjs`
   因外链变假绿）全落在最容易出事的地方。除非上下文真的不够用，否则不值。

### 8.4 执行顺序

1. **换行统一 + `.gitattributes`** —— 零逻辑改动，一个提交，跑一遍全量回归确认无 diff 噪音。
2. **CSS 原样外移** —— 逐字节比对，单独提交。
3. **CSS 去重 306 → 0** —— 有回归风险，单独提交，明暗两态截图比对（v135 起只有一套主题）。
4. **改动地图** `CHANGE-MAP`（第 5 步新建，放 `docs/` 下）—— 每个功能一栏：涉及的函数、必须同步的几处
   （如 `normalizeState` / `mergeStates` / `repairBackup`）、对应的 e2e 脚本。维护成本是
   每次加功能补一行，换来的是不用每次从头 grep。
5. **JS 分文件** —— 暂不做，等上下文真不够用再说。

**验收**：第 7 节那份清单照旧，另加一条——改完之后 `git diff --stat` 里不应出现
「整文件级换行变化」（那种 diff 会淹没真实改动）。
