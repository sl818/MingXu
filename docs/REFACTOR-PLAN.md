# 重构评估 · 单文件拆分

最后更新：v114（2026-11-17）

> **结论写在最前面**：不要做「拆页面」式重构——这个项目没有页面可拆。
> 要做的是「分段抽取」：**CSS 先外移（推荐立刻做）→ JS 分文件（看还需不需要大改）→ ES 模块化（不建议）**。
>
> 本文是评估记录，不是待办清单。真要动手前先读完第 3 节的成本。

---

## 1. 实测规模（v103）

| 部分 | 行数 | 占比 |
|---|---|---|
| JS（一个 `<script>` 块） | 13,851 | 78% |
| CSS（六个 `<style>` 块） | 3,808 | 21% |
| HTML 骨架 | 约 66 | 0.4% |
| 合计 | **17,772** | |

其他计数：**476 个顶层函数**、**182 个 `ACTIONS` 键**、**23 个后端接口**、129 处顶层 `const` / `let`。

**第一个结论**：这个文件不是「一个 HTML 页面」，而是一个 13.8k 行的 JS 应用，HTML 只有 66 行骨架，
其余界面全靠 JS 拼字符串。所以「拆页面」这个说法本身不成立。

---

## 2. 三个真实的结构问题

### 2.1 CSS 按「版本」分层，不按「模块」

六个 `<style>` 块依次是：

| 块 | 量级 | 来历 |
|---|---|---|
| 无 id（基础层） | 约 720 行 | 最早的一版 |
| `id="visual-v2"` | 约 1,560 行 | v2 视觉重构 |
| `id="skins"` | 约 300 行 | 皮肤变量层 |
| `id="new-pages"` | 约 420 行 | 清债 / 体重等新页面 |
| `id="layout-v3"` | 约 340 行 | 布局第三版 |
| `id="notify-v33"` | 约 470 行 | 通知 / 命令面板 |

后一版覆盖前一版，**生效完全依赖源码顺序**。全站有 166 个选择器被重复定义
（`.sidebar` 三次、`.habit-card` 两套），改样式时如果只改到前面那一份，
现象就是「改了没反应」。

这是目前**最大的结构性债务**，比「文件大」严重得多。

### 2.2 JS 是一个单作用域

476 个函数直接互调，没有任何 import / export。最大的几个是 `viewStats`（约 290 行）、
`goView`（约 270 行）、`viewToday`（约 195 行）、`mergeStates`（约 190 行）、`habitCard`（约 185 行）。

好处是改起来不用管依赖图；坏处是无法判断「动这个函数会影响谁」。

### 2.3 `ACTIONS` 是一张横切表

`ACTIONS` 约 1,300 行，所有模块的点击入口都平铺在里面：习惯、待办、清债、用药混在一起。

**这条决定了「按页面拆文件」拆不干净**——模块自己的渲染函数在各自文件里，
但它的入口在中央大表里。要么把 `ACTIONS` 也按模块切成多个对象再合并，要么保留单一表。

## 3. 拆的真实成本（具体到工具，不是空谈）

| 影响面 | 说明 |
|---|---|
| `_check_script.mjs` | 只解析**内联** `<script>`，带 `src` 的直接跳过。JS 外置后它读不到 `ACTIONS`，「data-act 漏 handler」这项检查会变成假绿 |
| `check-doc-anchors.py` | 它去 index.html 里找函数名和类名，符号搬走后锚点全报错 |
| SW 缓存清单 | `ASSETS` 要列全，漏一个就白屏，且只在二次访问 / 断网时暴露 |
| 部署 | 从「一个文件」变「十几个文件」，漏传过一次 `skin-cloud.css`，三套主题全没样式 |
| **样式顺序** | 主题 CSS 的 `<link>` 在当前六个 `<style>` 块**之后**加载。外移的 CSS 必须插在主题链接之前，否则内联样式反压主题——最容易悄悄搞坏的一处 |

## 4. 分三阶段

### 阶段 0 · CSS 抽取（推荐，先做这个）

把 3,808 行 CSS 挪到一个外部文件，`<link>` 位置**放在主题那几个 link 之前**。

分两小步，别一步到位：

1. **原样外移**：一行内容都不改，只换位置。可逐字节比对，零逻辑风险。
2. **去重合并**：把 166 个重复选择器合成一条，保留最后生效的那份值。这一步有真实回归风险。

**验收**：三套对比度审计（页面 / 弹窗 / 命令卡）0 不达标 0 跳过 + 六套皮肤各截一张图对比。

### 阶段 1 · JS 分文件（看还需不需要大改）

**用普通 script 串联，不引入模块系统**：

```html
<script src="js/core.js"></script>
<script src="js/sync.js"></script>
<script src="js/habits.js"></script>
```

因为仍在同一全局作用域，476 个函数互调**一行都不用改**。这是本项目唯一合适的拆法。

建议切成 8–10 个、每个 800–2,000 行，大致按：核心工具 / 云同步与合并 / 习惯 / 待办 / 清债 /
用药 / 统计 / 日历与体重随笔 / 导航与启动。

**硬性规则：只搬位置，不改一行逻辑。** 每搬一块跑一遍全量回归。

前提是先补齐 `_check_script.mjs`（改成能读外链文件并汇总所有块里的 `ACTIONS`）。

### 阶段 2 · ES 模块化（不建议）

收益是真正的封装与依赖可见，成本是 476 个函数重新梳理 import / export，
并且彻底破坏「无构建」的简单性（本地双击 HTML 就能跑这一点也会失去）。

除非哪天要多人长期协作，否则不值。

| 如果 | 那么 |

| 希望别人能提 PR | 阶段 0 + 1，并在 CONTRIBUTING 里补一张模块地图 |

---

## 6. 明确不要做的事

1. **不要引入构建工具**（webpack / vite / rollup）。这个项目的价值之一就是「传上去就能跑」。
2. **不要为了「看起来整洁」整体重写**。13.8k 行里每一处奇怪写法背后基本都有一次事故。
3. **不要在拆分的同时改逻辑**。搬位置和改行为必须分成两个提交，否则出问题无法定位。
4. **不要按「页面」切分 JS**。见 2.3，`ACTIONS` 是横切的，按页面切必然留下跨文件调用。

## 7. 动手时的验收清单

- [ ] `node _check_script.mjs` 仍然能查 `ACTIONS`（不能因为外链而静默通过）
- [ ] `python e2e/check-doc-anchors.py` 通过（它需要同步改文件列表）
- [ ] `service-worker.js` 的 `ASSETS` 列全新增文件，`CACHE` 版本递增
- [ ] 三套对比度审计：0 不达标、0 跳过
- [ ] 六套皮肤 × 明暗各截一张图，与改前逐像素比对
- [ ] 全量 e2e：打卡 / 戒断 / 截止型 / 收尾 / 综合 / v15 / 移动端 / 批次 2-4 / 云系 / ICS / HTTP
- [ ] 线上 md5 与本地一致（拆分后 index.html 会变小，但 SW 与其余文件必须同步）
