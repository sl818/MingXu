## 一、必须修（3 条）

### ① 组数改大时，补出来的默认提醒时间会与已有时间撞车 → 那一档提醒**根本发不出去**

**现象**：默认 3 组、时间点 `07:00 / 14:00 / 21:00`。把「每天几组」改成 4 并保存，
第 4 个时间点被自动补成 `21:00` —— **和第 3 个一模一样**。

**为什么是致命的**：真实推送的去重键是 `日期|kind|id|时刻`（`api/push.php:653`），
落库唯一键 `(user_id, slot_key, channel)`（`db/migrations/2026-10-29_push.sql:19`、
`2026-11-19_notify_channel.sql:23`）。两个时间点相同 → 两条的 slot_key 相同 →
第二条被唯一索引挡掉（`rowCount < 1` → `skipped`）。
**结果：用户设了 4 组，那一档只会收到 1 条提醒**；日历订阅里还会出现两条同一时刻的事件（UID 不同）。

**复现**：478 页 → 设置区「每天几组」4 → 保存设置 → 看提醒区第 4 个框 = `21:00`。

**根因**：`index.html:16528` `saveBreatheSettings()` 补默认点时直接取
`breatheDefaultTimes(groups)` 的末位值（`21:00`），**没有避开已占用的时刻**。

**建议**：补点时逐个跳过已用时刻；实在排不下（12 组挤满一天）就提示用户手填，
不要静默产生重复。另外后端 `api/schedule.php:344` 也应做一次去重兜底。

---

### ② 组数填超过上限（>12）时，点「保存设置」**毫无反应**

**现象**：在「每天几组」填 `13` → 下面的联动提示已经显示「每天 12 组」→
点「保存设置」→ **什么都没发生**：不保存、不弹 toast，只剩浏览器原生的「值超出范围」提示。

**根因**：`<input max="12">`（`index.html:8088`）触发 HTML5 原生表单校验，
**在 submit 事件之前就把提交拦掉了**；而 `saveBreatheSettings()` 里其实已经 `clamp(…, 1, 12)`
（`index.html:16528`），根本走不到。

**复现**：设置区「每天几组」填 13 → 点「保存设置」→ 观察无 toast、刷新后仍是旧值。

**建议**：两种改法任选 —— ① 把 `max` 去掉，靠保存时的 `clamp` 收敛（并在输入时把值夹住）；
② 监听 `invalid` 事件，把提示改成中文并给出手动修正后的值。

---

### ③ 改了组数但没保存设置就去保存提醒 → 新填的时间点被**静默丢弃**

**现象**：把组数改成 5（**不点保存设置**）→ 提醒区自动变成 5 个框 → 在第 4 个填 `17:45`
→ 点「保存提醒设置」→ 存回去的只有 3 个时间点，`17:45` **没了**，页面上也没有任何提示。

**根因**：`saveBreatheNotify()`（`index.html:16552`）用的是**已保存的** `m.groups`
（`index.html:16560` 的 `breatheGroups(m)`），只读 `bt0…bt{groups-1}`，
界面上多出来的那几个框在保存时被无视。

**建议**：保存提醒时以**界面上实际存在的输入框**为准（按 `name="btN"` 扫一遍），
并同步把组数一起写回；或者在设置区组数改动未保存时，提示「先保存设置再改提醒」。

## 二、建议修（4 条）

### ④ 「全部」档的达标率口径与页面上的算法说明对不上

- **说明文字**（`index.html:8185`）：「全部达标率 = 达标天数 ÷ 全部天数（没记录的日子算 0）」
- **实际实现**（`breatheRangeAgg`，`index.html:8099`）：`R = 0`（全部）时，
  `dates` **只收有记录的日子**，分母是「有记录的天数」，没记录的日子根本没进分母。
- 近 7 天 / 近 1 月 / 近 3 月三档是对的（分母含无记录的日子），**只有「全部」档口径不同**。
- 结果：只要有几天达标，「全部」档的达标率会明显高于说明文字承诺的值。

**建议**：要么把全部档也按「从第一天到今天」铺满分母，要么把说明文字改成
「全部达标率 = 达标天数 ÷ 有记录的天数」。

### ⑤ 云端加载「没有 schemaVersion 的老数据」时，478 的「每天几组」会被重置成 1

**实测**：同一份老数据（habits 里 `h_breathe.target = 3`、名字被改成「我的睡前呼吸」）：
- `schemaVersion: 6` → 组数 **3** ✓ 保住
- **没有 schemaVersion** → 组数 **1** ✗ 被抹掉（循环次数 5 保住、提醒时间从旧 `suggestTime` 迁进第一个 ✓）

**根因（顺序问题）**：
1. `migrateState()` → `ensureBreathingHabit()`（`index.html:448`）里 **`h.target = 1;`**
   （`index.html:463`）—— 这是 v170 当年「把 478 冻结成锚点、target 不再有意义」时加的；
2. 之后 `ensureModules()`（`index.html:1361`）才从锚点里提取组数
   （`moduleFromLegacy`：`m.groups = clamp(parseInt(h.target,10) || 1, 1, 99)`）——
   **这时 target 已经被抹成 1 了**。

> 补充：走**导入备份**（`repairBackup`）这条路不受影响，实测老备份导入后组数是 3 ✓；
> 受影响的是「正常加载一份很老的数据」这条路。

**建议**：在 `ensureBreathingHabit()` 抹 target 之前，先把 `h.target` 存进
`data.modules.breathe.groups`；或给 `migrateState` 补一个 v7 迁移步骤。

### ⑥ 首页横幅的文案不准 + 与「每天 N 次推送」的模型不一致

- **文案**：今天已经做了 1 组（共 3 组）时，横幅写「「478呼吸法」还没打卡」（`index.html:4616`–`4629`）。
  实际是「还没达标」，不是「没打卡」。
- **次数**：横幅只在**第一个**提醒点（`suggestTime` = `notifyTimes[0]`）之后出现一次，
  第二、第三个提醒点在横幅上没有任何体现 —— 和「每天固定时间推送 N 次」的新模型对不上。

**建议**：文案改成「今天还差 N 组」；提醒点判断改成「任一提醒点已过且未达标」。

### ⑦ 提醒区的「提醒渠道」勾了不生效，渠道卡片本身却没有任何说明

- 真实推送走的是全局通知通道矩阵 `notify_prefs[kind][channel]`（`api/push.php:667`），
  **不读** `modules.breathe.notifyChannels`；而且 478 / 喝水 / 普通习惯的 kind 都是 `habit`，
  共用一个通道开关 —— 用户在通知配置里把「习惯」类关掉，478 也就一起不发。
- 页面上只有一句小字「真实推送通道稍后开放」（`index.html:8189` 区块内），
  **渠道卡片本身没有任何提示**，容易被当成已经生效。
- 这一点是陛下早就说过的「通知路由以后做」，本身不是 bug，但**文案要更诚实**。
