## 二、必须修 3 条

### ① 默认提醒点撞车 → 新增「补点去重」函数

**根因**：`saveBreatheSettings()` 补点时直接取 `dflt[i]`，而 `dflt` 的**末位恒为 21:00**，
旧数组末位通常也是 21:00 → 扩容必撞。实测：3→4 组 = `07:00/14:00/21:00/**21:00**`。

**改法**：新增 `breatheFillTimes(olds, k)`（放在 `breatheDefaultTimes` 旁），三段取点：

```
① 先收旧值：合法的、且彼此不重复的，按原顺序，最多 k 个
② 还差几个 → 从 dflt(k) 里按顺序取「还没被占用」的那个
③ 还差几个 → 在 07:00–21:00 每 5 分钟扫，找第一个空档
   （k ≤ 5 时最多 5 个点，07:00–21:00 有 169 个 5 分钟档，第③步永远够用）
```

- `saveBreatheSettings()` / `saveBreatheNotify()` / `syncBreatheTimes()` 全部改走它。
- **用户手动把两个框设成相同时**：保存前做一次查重，撞了就**自动错开 5 分钟**并在提示行说明
  （「已把第 3 个提醒时间错开为 21:05，避免重复」），而不是默默存两个一样的。

**为什么不干脆"扩容时整体重算 dflt(k)"**：那会把用户已经改过的前几个时间点冲掉（比如他把 07:00 改成 06:30，扩容后被重置）——更糟。

**验收**：3→4、3→5、4→5 三条扩容路径，补出来的点两两不同；手动造重复时刻保存后不重复。

---

### ② 组数填超上限点保存没反应

**根因**：`<input max="12">` 触发 HTML5 原生校验，**在 submit 之前**就把提交拦了，
代码里的 `clamp(…, 1, 12)` 根本走不到。

**改法（三处一起，缺一不可）**：
1. 表单加 `novalidate`（`<form id="breathe-settings-form" novalidate>`）→ 提交不再被原生校验拦；
2. 输入框去掉 `max`（`min="1"` 留着），避免浏览器的红色气泡；
3. 保存时 `clamp` 到 5，**并把夹住后的值回填进输入框** + toast 说清楚：
   「已保存 · 每天几组按上限改为 5 组」。

> 上限改成 5 之后，这条的触发门槛从"填 13"降到"填 6"，**更容易踩**，所以必须同批修掉。

---

### ③ 改组数不保存 → 保存提醒丢时间点

**根因**：`saveBreatheNotify()` 用**已保存的** `m.groups` 去读 `bt0…bt{groups-1}`，界面上多出来的框被无视。

**改法**：
- 改成**扫界面上实际存在的输入框**（`[name^="bt"]`），有多少收多少，按框序号对应第几组；
- 收上来的框数若与已保存的组数不一致 → **一并把组数写成框数**（用户既然填了第 4 个框，意图很明显），
  toast 说明：「提醒设置已保存 · 每天几组同步为 4」。

## 三、建议修 4 条（方案含两个待陛下二选一）

### ④ 「全部」档达标率口径与文案不符

- 现状：说明写「÷ 全部天数（没记录的日子算 0）」，实现用的分母是**有记录的天数**（`breatheRangeAgg()` `index.html:8099`）。
- **方案 A（我推荐）**：文案改成「全部达标率 = 达标天数 ÷ **有记录的天数**」，实现不动。
  理由：把没记录的日子算进分母，老用户的历史达标率会被拉到很难看，没有参考价值。
- **方案 B**：实现改成从"最早有记录那天"铺到今天的全部天数，文案不动。数字会低很多。
- ✅ **陛下已定：方案 A**（18:55 确认）—— 只改文案，实现不动。

### ⑤ 云端加载无 schemaVersion 的老数据 → 组数被重置为 1

**根因顺序**：`ensureBreathingHabit()`（`index.html:448`）在 `index.html:463` 硬写 `h.target = 1`，
而 `ensureModules()`（`index.html:1361`）**之后**才从锚点提取组数 → 提取到的已是 1。

**改法**：在 `ensureBreathingHabit()` 抹 `target` **之前**先把它搬进模块配置：

```
ensureBreathingHabit(data):
  先确保 data.modules 存在（没有就建 { breathe: {} }）
  若 data.modules.breathe.groups 为空 且 h.target > 1 → 写进 data.modules.breathe.groups
  然后才抹 h.target = 1（锚点冻结的老规矩不变）
```

- 顺带：`moduleFromLegacy()` 那条路径（老备份导入）实测本来就是好的，只需把 `clamp(1,99)` 收到 `1,5`。
- **风险**：这是所有老用户的加载路径，必须跑导入/迁移回归（`verify-import-keep.py` + 造一份无 schemaVersion 的老数据实测）。

### ⑥ 首页横幅：文案不准 + 只催一次

- **文案**：「「478呼吸法」还没打卡」→ 改成「今天还差 N 组」（`index.html:4616`–`4629`）。
- **次数**：现在只按 `suggestTime`（= 第一个提醒点）判断一次；改成**用 `notifyTimes` 全部判断**——
  任一提醒点已过、且当天组数 < 目标 → 就催。

### ⑦ 提醒渠道勾了不生效

- 真实推送看的是全局通道矩阵 `notify_prefs[kind][channel]`（`api/push.php:667`），478/喝水/普通习惯共用 `habit` 一个开关。
- **改法**：渠道卡片下加一行小字：「渠道由「设置 › 通知配置」里的**习惯类**统一控制；这里勾选仅作记录」。
  （不改行为——通知路由本来就是陛下说"以后做"的那批。）

## 八、风险与遗留（动手前请过目）

1. **上限一刀切**：陛下确认老用户没有超过 5 组的数据 → 收紧 clamp 不会动到任何人的设置；
   但以后若有人手工改坏数据（groups=9），加载时会被夹回 5（现在夹到 99 不管）——这正是我们要的。
2. **① 的改动会动到"保留用户已改时间点"的行为**：改完仍是"旧值优先、只补不缺"，用户改过的点不会丢。
3. **② 去掉原生校验后**，用户填 8 会"看起来存了、实际被夹到 5"，所以必须带 toast + 输入框回填，否则又是另一种"点了没反应"。
4. **⑤ 动的是所有老用户的加载路径**，风险最高的一项 → 单独一批、单独回归。
5. **⑩ 是全局组件**，改了喝水/运动页的趋势图网格线颜色 → 三个页面都要截图核对，别只看 478。
6. **通知路由仍未做**（陛下定的"以后做"）：这批只保证 478 的提醒**时间点**正确、UI 诚实，真实推送渠道仍由全局矩阵决定。
