# 库存数据错乱事故复盘与修复（v31）

- 发生时间：2026-10-26 前后（用户报告于 2026-10-27 晚）
- 影响：用药库存与实际剩余不符，统计页看不到用药记录，用户按错误的库存判断而吃错药
- 结论：**不是偶发丢失，是两处代码缺陷叠加**。多设备是触发器，不是唯一原因。

---

## 一、两个根因（都有代码位置）

### 根因 A：冲突合并把当天用药记录压成 0 —— 最严重

`mergeStates()` 里，`checks`（打卡次数）和 `doses`（服药记录）用了同一段合并代码：

```js
['checks', 'doses'].forEach(key => {
  ...
  m[hid] = Math.max(Number(m[hid]) || 0, Number(l[day][hid]) || 0);
});
```

但两者层级根本不同：

| 字段 | 结构 | 这段代码的效果 |
|---|---|---|
| `checks` | `{日期: {习惯id: 次数}}` | 正确，次数取大 |
| `doses` | `{日期: {药品id: {时段: 记录}}}` | **`Number({})` = NaN → 0，整个药品当天的服药记录被压成数字 `0`** |

也就是说：**只要发生一次保存冲突（409），当天所有药的服药记录就归零。**

这直接解释了两件事：
- 统计里「用药」不计算（记录本身就是 0）
- 库存不动（没有记录可减）

### 根因 B：库存是个"绝对数"，合并时被整条丢弃

原来的库存存在 `med.stock` 里，每吃一次减一点。而 `mergeStates()` 对 `meds` 的处理是：

```js
r.forEach(item => map[item.id] = item);          // 以云端为基准
l.forEach(item => {
  if (!map[item.id]) map[item.id] = item;        // 只补新增
  else if (!cur.archivedAt && item.archivedAt) ... // 只合并归档标记
});
```

**除归档标记外，药品的其他字段一律以云端为准**，本地刚扣减的 `stock` 直接被丢弃。

即使根因 A 修好，只要 `stock` 还是绝对数，一次合并就会让扣减丢失，且**永久偏差**——系统不知道你手里到底有几片，没有任何办法纠正。

### 触发条件：两台设备

两台设备交替操作，几乎每次保存都撞 409 → 每次都丢扣减 / 压掉记录。即使只有一台设备，两个标签页或连续快速保存也会 409。

## 二、修复内容

### 1. 库存改为「基线 + 按记录推算」

不再存"剩余量"，只存两个值：

| 字段 | 含义 |
|---|---|
| `stockBase` | 某时刻手里实际有多少（用户显式登记） |
| `stockBaseAt` | 那个时刻 |

```
余量 = stockBase − 基线时刻之后所有服药记录累计的剂量
```

这样做的关键好处：**服药记录在合并时是并集（只增不减），所以任何设备算出来的余量必然一致，且可自愈**。即使某次写入丢了，下一次重算就纠正回来。撤销记录会自动退回余量，不需要"加回去"。

表单里「库存」改成「当前余量」，填的是"现在手里实际剩几片"；改这个数字等于重新登记一次基线，不动这个数字则保留原基线（避免把历史扣减"洗掉"）。

旧数据迁移：把原 `stock` 当作基线，迁移时刻设为当时，并打上「待核对」标记——**因为那个旧数字很可能已经不准了**。

### 2. 合并逻辑按结构分开处理

- `checks`：按天按习惯取较大值（原逻辑保留）
- `doses`：**多走一层，按时段并集**，两边都有的时段取本地那份
- `meds`：新增 `updatedAt`，按更新时间整体胜出；归档标记只增不减；库存基线额外比一次登记时间（取更晚的）

### 3. 用药写入操作日志

`takeDose` / `undoDose` 现在会写 `state.events`（带 `kind:'med'` 与 `slot`），统计页「打卡时间」里能看到 `💊 阿莫西林 · 08:00 +1`。同一分钟内的 +1 / −1 仍会合并成净变化，不刷屏。

### 4. 单设备登录

`api.php` 登录成功后把 `users.session_epoch + 1`。`lb_user()` 每次请求都会校验 epoch，旧设备的会话下一次请求即失效。

表现：旧设备弹回登录页，提示「这个账号已在其他设备登录，这台设备已退出（同一账号只允许一台设备在线）」。

- 同一浏览器多标签共享会话，不受影响
- 换设备 / 换浏览器登录会顶掉之前那台（这是需求本意）
- 注意：**这只能降低冲突概率，不能保证数据正确**。真正保证正确性的是第 1 条

## 四、部署（这次要传 4 个文件）

以前的版本只动前端两个文件。**这次包含后端改动，必须传 PHP**：

| 文件 | 改动 | 风险 |
|---|---|---|
| `api/bootstrap.php` | 区分「被顶替」的 401 | 传错会导致整站 500 |
| `api.php` | 登录时 epoch +1 | 同上 |
| `index.html` | 库存模型、合并、日志、迁移 | 前端，出问题可回滚 |
| `service-worker.js` | 缓存版本 v30 → v31 | — |

**建议顺序**（出问题好定位）：

1. 先备份这 4 个文件到 `.bak/时间戳/`
2. 先传 `api/bootstrap.php` 和 `api.php`
3. 立刻访问一次首页与登录页，确认不是 500
4. 再传 `index.html` 和 `service-worker.js`
5. 强制刷新一次（SW 缓存 v31 会接管）

如果第 3 步出现 500：把两个 PHP 文件按备份还原即可，前端不用动。

**不要**上传 `api/config.php`（含数据库口令），它这次没有改动。

## 五、上线后您需要做的一件事

打开用药页，看那 4 个药：

- 库存后面会显示 `· 待核对`，说明这个数字是从旧数据迁过来的，**不可信**
- 点开每个药，把「当前余量」改成**你现在数出来的实际片数**，保存
- 保存后「待核对」消失，从这一刻起按记录自动扣，剩余天数才会准

这四步做完，系统的库存才真正和实物对齐。

## 六、还没解决、但要知道的

1. **已经吃错的那次不会因为修复而回退**。系统只保证"从现在起算得对"。
2. **剩余天数依赖登记值**。如果登记的余量不准，天数也不准。建议每次开新盒时顺手更新一次。
3. **单设备会带来一个新麻烦**：如果您在手机上登录，电脑那台会被登出；反过来也是。这是需求本身，但用起来需要适应。
4. 旧 `med.stock` 字段**保留未删**（万一要回滚），但新代码不再读写它。
