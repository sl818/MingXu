### 两次值得记住的事故

**v31 库存错乱（10-27）**

`checks`（两层 `{日期:{习惯:次数}}`）和 `doses`（三层 `{日期:{药:{时段:记录}}}`）
用了同一段合并代码，`Number({})` 得到 `NaN → 0`，把整瓶药的当天记录压成 0。
之后改为「分开写」+「库存不存派生值」。完整复盘见 `docs/reports/库存事故复盘-2026-10-27.md`。

**推送「一直收不到」（10-30，排查两小时）**

三层原因叠加：

1. `lb_push_send` 的 `$err` 和 `$type` 参数顺序错位，导致 `msgtype` 为空串，
   企业微信返回成功但**静默不显示**
2. `push_sent` 的唯一索引实际不是唯一的，去重失效（每分钟重复发）
3. **最终元凶**：cron 脚本里带了 `--dry`，定时任务从上线起一直在「预演」，从没真发过

教训：给用户的排查命令带 `--dry` 时，必须强调「正式 cron 要去掉」。

## 接手须知

1. **先读 [ARCHITECTURE.md](ARCHITECTURE.md) 的四条不变量**，尤其「改前端必须推进 SW 缓存名」。
2. **改代码前先 `git log` 看最近的提交**，很多决定在 commit message 里写了为什么。
3. **`index.html` 是 CRLF**，用脚本改必须 `newline=''`（详见 ARCHITECTURE 不变量 4）。
4. **加字段要同步四处**：`normalizeState` / `mergeStates` / `ics.php` + `buildICS` / `schedule.php`。
5. **交付前自检**：`node _check_script.mjs` → 相关 e2e → 推进 SW → 打包。
6. **涉及部署命令时**，把「要不要跑 SQL」「要不要改 cron」讲清楚，
   并在给带 `--dry` 的排查命令时强调「正式任务要去掉」。

## 历史记录（2026-10-23 及更早）

以下是项目早期的关键决定，只保留仍然有效的部分。

**存储方案演变**

- 早期：纯 `localStorage` 单机
- 中期：可选云同步（本地 + 云端双写，有冲突选择弹窗）
- 现在：**云端唯一数据源**（方案 A）。本地只留主题偏好和登录元信息。
  旧本地数据在「云端为空」时首次登录自动上传一次，成功后删除。

**账号体系**

- 邀请码注册（管理员可开关、可换码）
- 密码最低 8 位
- **单设备登录**：`session_epoch` 每登录一次 +1，旧设备下次请求被踢
- 管理员只能管账号，不能读看板数据

**布局演变**

- 最初单列 → 双列 → 三种布局（top / side / wide）
- 手机底部从 5 tab 改到 4 tab + 悬浮「＋」+ 「更多」抽屉

**样式演变**

- 1 个 `<style>` → 6 个。每一轮都在文件尾追加新块覆盖旧规则，
  所以同名规则会定义多次——改样式时看 DevTools 的 Computed 面板确认来源，别按行号猜。

**主题演变**

- 4 套内置 → 9 套（4 套写在 `index.html` 的 `#skins` 块，5 套在 `themes/*.css`）

**已经去掉的功能**

- JSON 导入（设置页文案已声明不支持，`handleImport()` 成死代码）
- 本地离线模式
- 冲突选择弹窗（改成自动合并）
- 设置页的「更多页面」入口（v46 删除）
