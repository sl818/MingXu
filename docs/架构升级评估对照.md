# 架构升级评估对照

> 2026-11-27 建立。对外部文件《明序架构升级建议书》（538 行，微信传来，未纳入本仓）的逐条评估。
> 目的：保留这份建议里真正有价值的部分，同时把它的错误前提钉死，避免以后照着它执行走错路。
> 结论先行：**这份文件的方向感对（设边界、先数据后 UI、不引重框架），但它按「标准关系库应用」模板写成，没读懂明序的真实架构。适合当思路清单，不适合当执行方案。**

---

## 1. 三条前提判断错了

建议书的立论根基是「业务表缺 `user_id`、开放注册前要先打多租户地基」。这三条与现状不符。

| 建议书的说法 | 实际情况（已逐条核实） |
| --- | --- |
| 阶段 0.1：给 `habits` / `medications` 等业务表加 `user_id` | **业务表不存在**。全站数据存在 `boards.data` 一列 JSON 里；而 `boards` 表**本来就有 `user_id`**，后端按它读写 |
| 阶段 0.2：`UPDATE habits SET user_id = 1 WHERE user_id = 0` | 没有这种数据；且开放注册**已经完成**，不是「之前」 |
| 阶段 0.4：「开放注册前」安全检查清单 | 邀请码、注册/登录限速、CSRF、密码重置、单设备登录**全部已实现**，逐条 grep 过 `api.php` 与 `api/bootstrap.php` |
| 阶段 5：PWA 缓存按 `Authorization` 哈希隔离账号 | SW 明确**不缓存任何 API 响应**，只缓存 HTML/CSS/图标；项目用 session cookie，没有 Authorization |
| 阶段 6：千万级分区归档 | 按十几用户、自托管的规模，永远到不了这个量级 |
| 「476 个函数共享全局作用域」 | 主脚本在 IIFE 里（`index.html` 从 `<script>(function(){` 开始），不是裸全局；数字也过时，现在约 690 个函数 |
| `index.html` 约 1.78 万行、`api.php` 824 行 | 实际 `index.html` 20,477 行、`api.php` 1,227 行 |

**后果**：如果照阶段 0 执行，第一步就是去给不存在的表加字段——这不是「做得不好」，是「做不了」。

## 2. 和项目已定决策直接冲突

| 建议书 | 项目已定路线 | 冲突原因 |
| --- | --- | --- |
| 阶段 1 原生 ESM，`<script type="module">` | `docs/REFACTOR-PLAN.md`：「ES 模块化（不建议）」，定的是 CSS 外移 → JS 分文件 → 不做 ESM | 185 个键的中央 `ACTIONS` 表导致按页面拆不干净；ESM 会破坏「本地双击 HTML 就能跑」 |
| 阶段 2 Web Components + Shadow DOM | 一套主题、明暗两态，靠 `assets/theme-v2.css` 后加载覆盖 `app.css` | CSS 变量能穿透 Shadow DOM，但 `:root[data-theme="dark"] .btn` 这类覆盖进不去——主题系统会失效 |
| 「每新增一个组件就从旧文件删一段」 | 方向对，但 DOM 是 JS 拼字符串生成的，组件边界没有建议书假设的那么清晰 | 不能按文件物理删除对应代码 |

另外，刚做完三套对比度审计（页面 / 弹窗 / 命令卡），组件化要把审计整套重做。

## 3. 建议书里真正有价值、值得吸收的三点

1. **后端 action 映射表**：把 `api.php` 的巨型 `switch` 收敛成分发器 + 独立 handler。这个建议成立。但要说清性质——这是**工程整理**，不是**安全修复**；现有每个写操作都有 CSRF 和鉴权，没查出漏洞。
2. **越权测试清单**：「导出只返回当前用户数据」「登出后缓存不残留」值得写成自动化测试锁死。后端按 `boards.user_id` 读写，天然隔离，但值得验证而不是假设。
3. **事件委托、虚拟滚动、慢查询日志**：事件委托项目已在用；虚拟滚动对随笔 / 运动记录长列表可参考；慢查询日志在数据库几乎没查询的情况下优先级很低。

**动效方案（阶段 2.4）也基本对**：WAAPI、`transform`/`opacity`、`prefers-reduced-motion`——但这套项目里已经有了，见 `index.html` 的 `canAnimate` / `habitPulse`，不是新东西。

---

## 4. 建议书完全漏掉、但要紧的五件

1. **备份与恢复**：多用户场景下第一优先——每日 `mysqldump` + 异地存放 + 真的恢复演练。全篇 538 行没有一个字提备份。
2. **`mergeStates` 的合并口径收敛**：六套口径散在各字段上，v31（库存）、v78（导入删数据）、v198（记录复活）三次事故全出在这里。
3. **版本号四处同步**：`index.html` 的 `?v=NNN` 与 `APP_VERSION`、SW 的 `CACHE` 与 `VER`，漏一次就是「改了没生效」。
4. **172 个 e2e 测试本身的维护负担**：测试从「保障」变成「负担」的拐点已经过了。
5. **CSS 跨层覆盖**：`app.css` → `theme-v2.css` 后加载压裸类名，是「改一处坏三处」的根源。

## 5. 按真实场景重排的优先级

用户规模：十几用户、自托管分发、长期但不保证一直用。据此重排：

| 优先级 | 事项 | 说明 |
| --- | --- | --- |
| 1 | 备份与恢复 | 唯一紧急项；没演练过的备份不算备份 |
| 2 | 只读实测 `boards.data` 字节分布 + 2MB 告警 | 把「离 4MB 还有多远」从估算变实数 |
| 3 | `mergeStates` 合并口径收敛成一张表 + 一个函数 | 防数据事故，比拆前端重要 |
| 4 | 后端 action 映射表收敛 | 建议书里唯一值得采纳的工程项，可慢慢做 |
| 5 | 组件规范 + 日期控件 + 动效规范 | 见 `docs/组件规范与日期控件待办.md` |
| 6 | 原生 ESM / Web Components / 千万级分区 | **不做**，和规模不匹配 |
