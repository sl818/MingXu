# 组件规范与日期控件待办

> 2026-11-27 建立。状态：**待实施**。
> 基线：`index.html` 20,477 行、CSS 已外移、`service-worker.js` 到 v202；无构建、无 CDN、无框架。
> 原则：**不加框架、不加构建；老代码不动，新功能与改到的地方先用新规范。**
> 本文件只约束新代码与改到的地方，老代码逐步迁移，**不做全量替换**。

---

## 0. 先分清三样东西的落点

最常见的误解是把这三件打包成一个「组件库文件」然后「需要时引入」。实际上只有一样符合这个模式。

| 事项 | 落点 | 性质 |
| --- | --- | --- |
| **日期控件** | 新增 `assets/vendor/` 三个文件，`index.html` 引入 | 唯一一个「新文件 + 按需引入」的外部库 |
| **组件规范** | 改 `app.css` / `theme-v2.css` + 在 `index.html` 的 IIFE 里加一组小函数 | 改现有文件，是**写法约定**；不主动把老代码改成 `UI.btn(...)` 就永远用不上 |
| **动效** | 在现有打卡 / 操作处插几行调用 | 根本不是库；触发时机与 `render()` 重绘顺序绑死，写成独立库反而不知道何时触发 |

一句话：**只有日期控件是「新文件 + 引入」，组件规范是「改写法」，动效是「改时序」。**

## 1. 组件规范

### 1.1 CSS 组件层（写进现有 CSS）

基于现有主题变量（`assets/theme-v2.css` 定义，浅色 / 深色两态），把散落的写法收敛成固定变体：

- `.btn`：primary / ghost / danger / sm / icon / loading
- `.field`：统一 `label + control + hint + error` 四段结构
- 待新增 `.select`、`.switch`、`.segmented`、`.modal`、`.toast`：各定义一套

**颜色一律 `var(--accent)` / `var(--surface)`，不写死十六进制。**

**层叠坑（必须记住）**：`theme-v2.css` 加载在 `app.css` 之后，其中有一条裸 `.btn` 规则。新增带后缀的变体（`.btn.icon` / `.btn.loading`）不会被压；但**改 `.btn` 基础规则不会生效**，必须带 `:root[data-theme]` 前缀，或者直接改在 `theme-v2.css`。旧皮肤时代要带 `:root[data-skin]` 前缀，该机制已删除。

旧类名全部保留，**不批量重命名**。

### 1.2 JS UI 工厂（放进 `index.html` 的 IIFE，只返回 HTML 字符串）

```js
const UI = {
  btn(label, o = {}) {
    return '<button type="button" class="btn ' + (o.variant || '') + '"'
      + ' data-act="' + esc(o.act || '') + '"'
      + (o.must ? ' data-must-settle="1"' : '') + '>' + esc(label) + '</button>';
  },
  field(label, control, o = {}) {
    return '<label class="field ' + (o.wide ? 'wide' : '') + '"><span>' + esc(label) + '</span>'
      + control
      + (o.hint ? '<small class="f-sub">' + esc(o.hint) + '</small>' : '') + '</label>';
  },
  select(name, opts, val) { /* 生成 <select>，值统一 esc() */ },
  date(name, val, o = {}) { /* 见第 2 节 */ }
};
```

**安全陷阱**：`field(label, control)` 里 `label` 自动转义，`control` 却直接插原始 HTML。调用方容易误以为整体安全，把未转义的用户内容塞进 `control`。API 要么把参数改名为 `rawControl`，要么整个字段改成传值不传 HTML。

### 1.3 事件约定

组件只产出 `data-act`，分发沿用现有委托（`ACTIONS` 表），表单提交沿用现有 `submit` 分支。`UI` **不接管任何业务逻辑**，只管外观。

### 1.4 能力边界（必须认清）

`UI` 工厂只是模板字符串函数的升级版，解决「外观一致」，**解决不了行为一致**。真正让代码变乱的是散落的 `sync*` 表单联动函数，工厂碰不到它们。不要期待「加了组件规范以后加功能就轻松」——它不会。

## 2. 日期控件

### 2.1 为什么值得引入

原生 `<input type="date">` / `type="time">` 全站有几十处，能用但样式不可控、无范围选择、无快捷预设。flatpickr 约 20KB、免构建、中文与键盘支持成熟，是这类项目最划算的外部依赖。**不引 CDN，本地托管。**

### 2.2 接线步骤

1. 下载 `flatpickr.min.js` / `flatpickr.min.css` / `zh.js` 到 `assets/vendor/`。
2. **CSS 加载顺序**：flatpickr 的 CSS 放在 `index.html` 里 `app.css` 的 `<link>` **之前**，这样本项目自己的覆盖样式才能压掉库样式。
3. `service-worker.js` 的 `ASSETS` 加入这三个文件；`CACHE` 与 `VER` 从 v202 递增。**版本号四处同步**：`index.html` 的 `?v=NNN`（replace_all）与 `APP_VERSION`、SW 的 `CACHE` 与 `VER`。
4. 待新增 `mount()` 函数：`UI.date()` 输出 `<input type="text" data-ui-date ...>`；mount 时判断 `matchMedia('(pointer: coarse)').matches`：手机改回 `type="date"` 用系统原生，桌面初始化 flatpickr。
5. 配置 `dateFormat: 'Y-m-d'`，值写回**原 input 的 `value`**；现有 `FormData(form)` 与 `save*Form()` 都不用改。若开 `altInput` 显示中文，提交的仍是原 input。
6. 时间输入先用原生 `<input type="time">` + 统一 CSS，暂不引入 flatpickr 的 `enableTime`。

### 2.3 主题映射（写进 `app.css`）

```css
.flatpickr-calendar{
  --fp-bg:var(--surface);
  --fp-text-color:var(--text);
  --fp-border-color:var(--line);
  --fp-nav-color:var(--muted);
  background:var(--surface);
  border-color:var(--line);
}
.flatpickr-day.selected{background:var(--accent);border-color:var(--accent)}
```

上面只映射了五个变量；flatpickr 还有 `--fp-day-bg`、`--fp-day-hover`、`--fp-today-color` 等，落地时按明暗两态实测补齐。

### 2.4 移动端降级的真实代价

手机用系统原生、桌面用 flatpickr，等于「统一组件」在移动端**并不统一**。而且 `UI.date()` 首屏输出 `type="text"`、`mount()` 时才改成 `type="date"`；JS 慢或出错时用户看到文本框。这个取舍要认，不要自欺。

## 3. 动效规范

### 3.1 项目已有正确做法，不要推翻

`index.html` 的 `canAnimate` / `habitPulse`（约 4216 行起）已经是正确模式，注释写得很直白：

> render() 会重建整张卡，所以动效必须排在重绘之后，用 WAAPI 打在重建出来的节点上（CSS 动画会随重绘重放，反而变成噪音）。

因此：

- **进场 / 退场**（弹窗、提示卡）用 CSS keyframes，项目已有 `fadeIn` / `popIn`。
- **一次性反馈**（打卡脉冲、数值变化）用 WAAPI（`element.animate()`），在 `render()` 之后用 `requestAnimationFrame` 打节点。
- **不要「动效全部 CSS 化」**——在 `render()` 全量重绘架构下，CSS 动画每次跟着重播，会变成噪音。
- 尊重 `prefers-reduced-motion`，沿用 `canAnimate()` 判断；关掉时只震动、不放大。

### 3.2 新增动效的落点

照 `habitPulse` 模式在对应操作里插调用即可，**不做独立动效库文件**。动效触发时机跟重绘顺序绑死，抽成库反而不知道何时触发。

## 4. 四个必须处理的坑

1. **`render()` 全量重绘会留下 flatpickr 实例**：必须在 `render()` 开头 destroy、结尾 mount，做成幂等。注意 `render()` 有骨架 / landing 等**提前 return 分支**，mount 要放在所有出口都调用的小函数里，不能只在末尾。
2. **弹窗是独立生命周期**：`openModal()` / `closeModal()` 分别要 mount / destroy；很多操作是 `save(); render(); closeModal();` 连续调用，时机要对。
3. **`data-act` 挂在原 input**：不要挂到 flatpickr 生成的 `altInput` 上，否则事件委托拿不到。
4. **e2e 里十余份脚本硬编码旧 `SKINS` 列表**，跑的是不存在的皮肤键，等于只测了一套。加完组件 / 动效后拿这些脚本做「对比度回归」不可靠，要先修列表。

## 5. 落地顺序与验收

1. 先写 CSS 组件层与 `UI` 工厂，新功能先用。
2. 引入 flatpickr 并完成 SW 清单 / 四处版本号 / 主题映射。
3. 把 mount / destroy 接进 `render()` 的所有出口、`openModal()` / `closeModal()`。
4. 试点两个高频表单：**体重记录**、**运动记录**。
5. 跑 `verify-weight-*` / `verify-move-*` 的 e2e，确认 `input[name=date]` 取值不变；少数断言 `type="date"` 的测试要同步调整。
6. 按项目规矩，**改版要出前后对比网页**：改前截图、改后截图，拼成一页可切换 / 并排对比的 HTML，给用户看改了什么。
7. 稳定后再逐步扩散到其余日期输入。
