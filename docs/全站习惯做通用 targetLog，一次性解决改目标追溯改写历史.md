## 一、问题是什么

**历史里只存了「那天做了多少」，没存「那天目标是多少」。**

判定「某天是否达标」时，代码拿的是**当前设置**去套历史：

```js
// index.html · met(h, d)
const c = countOf(d, h.id);
return c >= Math.max(1, Number(h.target) || 1);   // ← h.target 是「现在」的值
```

于是：

| 时间 | 用户操作 | 那天实际 | 系统判定 |
|---|---|---|---|
| 9 月 | 设「每天 1 组」，做了 1 组 | 完成 | ✅ 达标 |
| 11-27 | 把目标改成「每天 3 组」 | — | — |
| 回看 9 月 | 什么都没改 | 还是那 1 组 | ❌ **变成不达标** |

**实测证据**（2026-11-27 线上拟真测试，测试账号 `test@sl00.top`）：

- 改目标前：全部档 完成度 **100%**、达标率 **100%**（那 2 天都达标）
- 把「每天几组」从 1 改成 3 后：同一批历史变成 达标率 **0%**、完成度掉到 44%
- 累计组数仍是 4 组、累计呼吸次数仍是 16 次（这两个是绝对量，不受影响）

用户的第一反应是「**我的数据丢了？**」，实际一天都没少。

### 1.1 这个机制要解决哪些问题 —— 三件里它只能解决两件

线上拟真测试（2026-11-27）之后留下 3 个待办（编号沿用 v204 的待办清单）。
它们看起来像同一件事，**但根因只有一半相同**：

| 编号 | 问题 | 根因 | targetLog 能解决吗 |
|---|---|---|---|
| **3** | 改目标后，历史达标率从 100% 掉到 0% | **目标口径**：拿当前 `target` 去判历史 | ✅ **能**（本机制的核心目标） |
| **5** | 喝水 / 运动同样被追溯改写（喝水更隐蔽，改「每杯多少 ml」也影响历史） | **同上**，只是各自的目标字段不同 | ✅ **能**（第 2 期，把 `perMl` / `tVal` 一起进 log） |
| **4** | 「全部」档显示完成度 100% / 达标率 100%，而近 90 天只有 2% —— 差 50 倍，很扎眼 | ❌ **完全不同**：这是**分母口径**问题（全部档分母 = 「有记录的天数」，不是「全部天数」） | ❌ **不能** |

#### 为什么问题 4 不是同一个根因

全部档的算法是：

```
全部档日期集 = 所有「有记录」的日子        ← 注意：不是从第一天到今天
达标率 = 达标天数 ÷ 有记录的天数
```

实测数据：只有 2 天有记录，那 2 天都达标 → 100%。**这个 100% 在当前口径下是算对的。**

即使做了 targetLog（历史按当天目标判），那 2 天仍然是"当天设 1 组、做了 1 组、达标" → **还是 100%**。

所以 **问题 4 需要单独拍板**，不要以为做完 targetLog 它就自动好了。

#### 问题 4 的三个选项（等 targetLog 之后单独定）

| 选项 | 做法 | 全部档会显示 | 代价 |
|---|---|---|---|
| **4-A 分母改成全部天数** | 从第一条记录到今天，无记录的日子算 0（与「近 N 天」同逻辑） | 约 3%（真实但难看） | 口径统一；但用户可能更沮丧「练了三个月才 3%」 |
| **4-B 不显示完成度/达标率** | 全部档只留累计组数、累计呼吸次数（绝对量） | 不显示百分比 | 最不容易误解；但少了"回顾成效"的入口 |
| **4-C 保持现状 + 更醒目标注** | 分母仍是「有记录的天数」，但在 KPI 上直接写「共 N 天有记录」 | 100%（旁边注明"2 天有记录"） | 零改动；但 100% 仍会误导 |

**倾向**：4-C 成本最低且不剥夺正面反馈（"我记录的日子里都做到了"），但必须把"N 天"显示出来。
**不建议** 4-A —— 它会让全部档的数字比任何区间档都难看，反而打击使用意愿。

**决策记录**：陛下 2026-11-27 定了「等 targetLog 做了再一起处理 3 / 4 / 5」。
本文只负责 3 和 5；4 的方案在 targetLog 落地后再定（三个选项已列在上面）。

## 二、各模块现状口径（这是本节最重要的事实）

「改目标会追溯改写历史」**不是 478 独有的**。逐个查过：

| 模块 | 判定依据 | 目标来源 | 改目标后历史会变吗 |
|---|---|---|---|
| **普通养成习惯** | `countOf(d) >= h.target` | `habits[].target`（当前值） | ❌ **会变** |
| **478 呼吸法** | 同上（`h_breathe.target`） | `modules.breathe.groups` 同步过来的当前值 | ❌ **会变** |
| **喝水** | `waterMlOf(...) >= waterGoalMl(h)` | `max(goalMl, 每天几杯 × 每杯 ml)`（**全是当前值**） | ❌ **会变**，而且更隐蔽：连「每杯多少 ml」都会影响历史 |
| **运动** | `moveSportDone(s, d)` → `moveProgress(s, d).val >= .target` | `sports[].tVal` / `targetSteps`（当前值） | ❌ **会变** |
| **用药** | `medTakenCount(d) >= medScheduledCount(d)` | 当天排期（按药品方案算出来的） | ✅ 不变（除非改用药方案本身） |
| **戒烟 / 戒除** | 看事件（有没有「抽了」）、看当天打卡 | 无「目标次数」概念 | ✅ 不变 |
| **清债（money）** | `paid / total` 进度百分比 | 债务本金 + 还款计划 | ⚠️ **变，但是另一回事**（见下） |

### 清债为什么不算同类问题

清债没有「每日达标」这个概念，它算的是**进度**：

```
已完成 = 已还金额 / 债务总额
```

你增加一笔债务（或调高计划金额），分母变大、进度百分比自然回退 —— 这**符合直觉**：
「我又借了钱，当然还没还完」。它不存在「9 月那天明明还了，现在说不算」这种事。

**所以：需要 targetLog 的是「每日达标型」（养成习惯 / 478 / 喝水 / 运动），
不需要的是「进度型」（清债）和「事件型」（戒烟 / 用药）。**

## 三、为什么必须一次做完，不能只改 478

`met()` 是**全站共用的判定入口**，这些地方都吃它：

- `dayStats(d)` → 每日完成率（首页 / 统计页的柱状图、完成率卡片）
- `rateOver(days)` → 区间完成率（统计页「近 N 天完成率」）
- `habitDayAcc` / `taskStats` → 各模块的达成统计
- `met()` 也决定「今天算不算完成」→ 影响首页横幅、提醒、导出备份的判定

如果只给 478 单独按历史目标算：

| 位置 | 478 那部分口径 |
|---|---|
| 478 页自己的达标率 | 按**历史目标**（正确） |
| 统计页「总完成率」里的 478 部分 | 仍按**当前目标**（旧口径） |
| 页面上的 478 达标率 | 又是历史目标 |

**同一个习惯三个数字** —— 比现在更糟。所以要么全站一起做，要么不做。

## 四、方案 B 设计

### 4.1 数据结构：记「变更」，不记「每日快照」

**不推荐**每天存一份目标快照（`checks[d].__target`）：
- 体积随天数线性涨（一年 365 条，哪怕目标从没变过）
- 污染 `checks` 的语义（它只该存「做了多少」）

**推荐**：每个习惯存一条**变更记录**，只在用户改目标时追加：

```js
habits: [
  {
    id: 'h_breathe',
    name: '478呼吸法',
    target: 3,
    targetLog: [                                  // ← 新增字段
      { at: '2026-09-01T00:00:00.000Z', v: 1 },
      { at: '2026-11-27T04:23:00.000Z', v: 3 }
    ]
  }
]
```

- `at`：变更生效时刻（ISO，UTC）
- `v`：变更后的目标值
- **第一条**用习惯创建时间（`createdAt`）当 `at`、`target` 当初值
- 体积：一次变更约 55 字节；一年改 20 次 ≈ 1.1 KB，可忽略

### 4.2 判定算法

```js
/* 某天 d 生效的目标值：取 at <= d 当天 23:59 的最后一条；没有记录就用当前 target 兜底 */
function targetOn(h, d) {
  const log = Array.isArray(h.targetLog) ? h.targetLog : null;
  const cur = Math.max(1, Number(h.target) || 1);
  if (!log || !log.length) return cur;            // 老数据兜底
  const end = d + 'T23:59:59.999Z';               // 当天结束（含当天改的目标）
  let best = null;
  log.forEach(function (e) {
    if (!e || typeof e.v === 'undefined') return;
    if (String(e.at || '') <= end) {
      if (!best || String(e.at) > String(best.at)) best = e;
    }
  });
  return best ? Math.max(1, Math.round(Number(best.v) || 1)) : cur;
}
```

`met()` 里只改一行：

```js
- return c >= Math.max(1, Number(h.target) || 1);
+ return c >= targetOn(h, d);
```

喝水 / 运动各自的目标函数同理（`waterGoalMl` 要按 `targetOn` 取当天的「杯数」再乘「当时的每杯 ml」——
**注意：每杯 ml 也是目标的一部分，也要进 log**）。

### 4.3 四条边界（必须先定死，否则做出来会踩新坑）

1. **当天改目标 → 当天按新目标判**。用户改目标就是想让今天按新标准，不能今天还按旧的。
   （实现上：`at <= d 23:59:59` 包含当天，天然成立。）
2. **跨天后前一天锁死**。昨天按 1 组算达标，今天起永远算达标。
3. **老数据没有 `targetLog`** → 用当前值兜底。**升级那一刻历史会重算一次**，之后稳定。
   想彻底避免只能反推历史目标，不建议（没有依据，等于编数据）。
4. **补记历史**（点过去某天补打卡）→ 用那天的目标，没有就用当前。
   ⚠️ 已知副作用：如果用户先改目标、再补记很久以前的日子，那天会按**当前**目标判（因为 log 里那天之前没有记录）。
   可接受，但要在文档里写明。

### 4.4 写入时机

- `saveBreatheSettings`（478）：`groups` 变化时追加一条
- `saveModuleForm`（模块弹窗）：同
- 喝水 / 运动的设置保存：杯数、每杯 ml、`tVal` / `targetSteps` 变化时追加
- 普通习惯编辑（`habitModal`）：`target` 变化时追加
- **只在值真的变了才写**，避免 log 变成垃圾场

写入辅助：

```js
function logTarget(h, v) {
  const nv = Math.max(1, Math.round(Number(v) || 1));
  if (!Array.isArray(h.targetLog)) h.targetLog = [];
  const last = h.targetLog[h.targetLog.length - 1];
  if (last && Number(last.v) === nv) return;              // 没变不写
  h.targetLog.push({ at: new Date().toISOString(), v: nv });
  if (h.targetLog.length > 200) h.targetLog = h.targetLog.slice(-200);  // 防无限增长
}
```

## 五、影响面清单（改的时候照着走，一处都不能漏）

### 5.1 数据结构三处（项目硬规则：新增顶层字段必改三处）

`targetLog` 挂在 `habits[]` 里（不是顶层），但仍要过这三道：

| 位置 | 要做什么 |
|---|---|
| `normalizeState()` | 每个习惯的 `targetLog` 做白名单清洗（`at` 必须是 ISO 字符串、`v` 是 1..99 的整数、按 `at` 排序、去掉重复 `at`） |
| `mergeStates()` | **按 `at` 并集去重**（两端各改过目标时不能丢），不能整组覆盖 |
| `repairBackup()` | 导入备份时保留 `targetLog`（`normalizeState` 已经覆盖，但要跑 `verify-import-keep.py` 确认没被洗掉） |

### 5.2 判定与统计

| 位置 | 改什么 |
|---|---|
| `met(h, d)` | `h.target` → `targetOn(h, d)` |
| `targetOn()` / `logTarget()` | 新增（放在 `met()` 上方） |
| `waterGoalMl(h)` | 杯数改取 `targetOn`；**每杯 ml 也要进 log**（新增 `perMlLog` 或把 log 的 `v` 改成对象） |
| `moveProgress(s, d)` | `s.tVal` → 按日期取的 log 值 |
| `dayStats()` / `rateOver()` / `habitDayAcc()` / `taskStats()` | 不用改代码（它们都走 `met()`），但**必须重跑测试确认口径** |
| `algoModal()` | **必须同步**：页面上的「达标算法」说明要改成「按当天生效的目标判定」（记忆硬规则：改 `met` 必同步 `algoModal`） |
| 478 的 `breatheStatsBody()` 算法说明 | 把 v204 新加的「改了每天几组，历史会重算」改成「按当天生效的目标算」 |
| 统计页各块（习惯 / 用药 / 喝水 / 运动 / 478 / 戒烟） | 文案里的「历史按当前设置折算」全部要改 |

### 5.3 提醒与日历（不受影响，但要验证）

- `buildICS()` / `api/ics.php` / `api/schedule.php` 只看**今天**的目标 → 不需要 targetLog
- 但如果 ICS 里带了「第 N 组」，改组数后历史事件不会变（日历是"从现在往后"的）✓
- 仍然要跑 `test-ics.php` / `test-schedule.php` / `verify-ics-subscribe.py` 确认没被误伤

### 5.4 导出与兼容

- 老客户端读到带 `targetLog` 的 state：`normalizeState` 是本机代码，刷新即更新 → 没问题
- 但如果**用户用旧手机没更新**，新数据的 `targetLog` 会被旧代码的 `normalizeState` 洗掉（旧代码不认识这个键）
  → **这是升级顺序风险**：建议在 `repairBackup` 里保留未知字段（已有兜底），并在发版说明里提示"先更新所有设备"

## 八、风险与不做的理由

| 风险 | 说明 | 缓解 |
|---|---|---|
| **口径分裂** | 只改 478 会造成三个数字打架 | 必须全站一起做（本文档的核心结论） |
| **升级顺序** | 旧设备可能洗掉 `targetLog` | 发版说明要求先更新所有设备；`repairBackup` 保留未知字段 |
| **"当天"的歧义** | 晚上 23:00 改目标，当天结果会翻转 | 边界 1 已定：当天按新目标。在算法说明里写明 |
| **复杂度** | `met()` 从一行变三层（log 查找 + 兜底） | `targetOn` 单测覆盖；性能可忽略（每天查一次，log ≤ 200 条） |
| **清债被误伤** | 清债是进度型，不需要 targetLog | 不改 `money` 任何逻辑 |

**为什么现在不做**：方案 A（文案标注 + 改目标时提示）已经把「用户误解」压到很低；
targetLog 是架构级改动（动 `met` + 三处数据结构 + 全站文案 + 三个模块的目标函数），
收益是「历史结论稳定」，但要付出一次全量回归的成本。等真的有人抱怨再说。
