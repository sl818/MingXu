# 全站「删除会不会被同步复活」盘点

> 创建：2026-11-26　相关版本：v198　定位：技术债清单，记录现状与后续做法。
> 背景：陛下是**每账号只允许一台设备在线**（新登录踢掉旧会话，后端 `api.php` 保存时先验会话、
> 被踢设备直接 401，走不到版本合并），所以**跨设备并发覆盖基本不会发生**；
> 但**同一台设备开两个标签页**与跨设备在数据层面等价，会真的触发合并。

## 一句话结论

墓碑机制目前只覆盖**运动记录**（v198 新加）+ **习惯 / 待办 / 用药**（项目原有的 `archivedAt`）。
**随笔、体重、事件流、心情、备注、以及各常驻模块的配置**都还没有 —— 在多标签页场景下，
这些地方「删掉的东西会被旧数据带回来」。

## 现状全表

| 数据 | 合并策略 | 删除做法 | 删了会被复活吗 |
| --- | --- | --- | --- |
| 习惯 habits | 按 id 并集 | 写 `archivedAt` 归档 | **不会**（归档标记只增不减） |
| 待办 tasks | 按 id 并集 | 写 `archivedAt` 归档 | **不会** |
| 用药 meds | 按 id 并集（有专门分支） | 写 `archivedAt` 归档 | **不会** |
| **运动记录 records** | **v198：按 id 逐条 + 墓碑优先** | **写 `deletedAt` 墓碑（30 天清理）** | **不会** |
| 运动实例 sports | 按 id 比 `updatedAt` | 真删（无墓碑） | **会**（实例从另一端回来） |
| 随笔 essays | 按 id 并集 | 真删 | **会** |
| 体重 weights | 按 id 并集 | 真删 | **会** |
| 事件 events / 烟瘾 cravings / 买烟 packs | 按 id 并集 | 真删 | **会** |
| 心情 moods / 备注 notes | 按天 / 整份带过 | 覆盖式 | 不适用（不是"一条一条"的东西） |
| 次数 checks / 跳过 skips / 剂量 doses | 按天合并，取大 / 并集 | 覆盖式 | 不适用 |
| 喝水 / 478 / 戒烟 / 运动的**模块配置** | 整块取新（模块级 `updatedAt`） | 覆盖式 | 会被整块覆盖（配置不是"一条条"，无处安放墓碑） |

## 三种合并策略的取舍

1. **整块取新**（模块级配置）：简单，但"谁最后动过谁赢"，对方任何改动都会带走你这一侧的其它改动。
   → v198 已给运动模块换成下面的第 3 种；其余模块仍是整块取新。
2. **按 id 并集**（随笔、体重、事件）：新增不丢，但**删除永远不生效** —— 对方那份旧数据会把它带回来。
3. **按 id 逐条 + 墓碑**（运动记录）：新增不丢、删除也不丢，是目前最完整的做法。

## 后续要做什么（按性价比排）

| 优先级 | 事项 | 代价 | 说明 |
| --- | --- | --- | --- |
| 高 | **随笔、体重**也用 `deletedAt` 墓碑 | 小 | 它们的合并已经按 id 走，只要在 `normalize` 登记墓碑 + 合并时墓碑优先即可，与运动记录同款 |
| 中 | 事件流（events / cravings / packs）同样处理 | 中 | 事件流有"同秒多条"的判重键，墓碑要挂在 id 上，改动比前两项多 |
| 中 | 运动实例也加墓碑 | 中 | 删除运动是低频操作，收益有限；且要改「删实例时记录怎么办」的语义 |
| 低 | 喝水 / 478 / 戒烟的模块配置也逐字段合并 | 大 | 配置是「一整块设置」，拆成字段级合并收益不明显 |
| 低 | **409 合并给用户提示** | 极小 | 现在自动保存时合并是**静默**的（只有手动保存才 toast），用户看不到数据被重排 —— 这条建议立刻做 |

## 已知的固有代价（与墓碑无关）

- **被踢下线设备上的未保存改动会丢**：会话失效 → 保存 401 → 刷新后整份拉云端 → 内存里的改动没了。
  实操建议：在 A 设备上刚改完没等同步完成，别在 B 设备登录。
- 墓碑本身会让数据里多留 30 天的"已删除"记录（运动记录），之后自动清理。
