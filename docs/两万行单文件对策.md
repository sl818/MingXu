# 两万行单文件对策

> 2026-11-27 建立。针对「`index.html` 已 20,477 行，后续还要继续加功能，该怎么办」的判断与可选路径。
> 结论先行：**2 万行不是病，是症状。真正让人累的是三件事——找不到、记不住同步点、改完怕碰坏别的。冲着行数去拆文件，治不到根上。**

---

## 1. 现状基线（核实于 2026-11-27）

| 项目 | 实测值 |
| --- | --- |
| `index.html` | 20,477 行 |
| 函数数量 | 约 690 个 |
| 脚本结构 | 3 个 `<script>`：前两个是首屏主题 / 安装探测的小脚本，第三个从第 100 行起是一个大 IIFE |
| `assets/app.css` | 4,267 行 |
| `assets/theme-v2.css` | 1,537 行 |
| 驱动方式 | `render()` 全量重绘 `#main` + 中央 `ACTIONS` 表（事件委托） |
| CSS 外移 | 已完成，剩下重量都压在 `index.html` |

**关键判断**：`render()` 全量重绘是很多问题的共同根——动效要做在重绘之后、日期控件要反复 mount/destroy、局部更新做不到。行数只是这个架构选择的结果。

---

## 2. 三条路径，客观对比

### 路径 A · 普通 script 分文件（不引入模块系统）

按模块切成 8–10 个 `.js` 文件，用普通 `<script src>` 按顺序串联，仍在同一全局作用域。

```html
<script src="js/core.js"></script>
<script src="js/sync.js"></script>
<script src="js/habits.js"></script>
```

- 收益：每次读的上下文变小；函数互调**一行都不用改**。
- 成本：部署从 1 个文件变 12 个；SW 清单漏一个就白屏；`_check_script.mjs` 因外链变假绿；**搜索范围一点没小**。
- 项目自有判断：`docs/REFACTOR-PLAN.md` 定为「暂不做」，理由是「只省上下文，不省搜索」。

### 路径 B · 完全不动，靠命名约定 + 文档纪律硬扛

- 收益：零成本、零风险、部署不变。
- 成本：越往后越难找、越容易撞名，「改一处坏三处」的概率缓慢上升。

### 路径 C · 上框架重写（Vue / React 组件化）

- 收益：真正的封装与依赖可见。
- 成本：2 万行重写、172 个测试作废、部署模型被破坏、主题层要重做。
- 判断：与当前规模不匹配，**不做**。

---

## 3. 推荐做法：B 为底 + 一个例外 + 三件小事

### 例外：把「纯算法」抽出去，而不是按页面拆

抽的是**不碰 DOM** 的那部分：`mergeStates`、`normalizeState`、`repairBackup`、统计聚合、日期计算。

- 理由：它们正是出过三次数据事故的地方（v31 库存、v78 导入删数据、v198 记录复活）。
- 做法：抽成 `js/core.js` 单独引入，可用 Node 直接跑单元测试，不必每次开浏览器。
- 边界：这是唯一一个「拆了就能立刻降低事故率」的动作。

**不要按页面拆文件**（习惯一个、待办一个）。它们共享 `state` 和 `render()`，拆开只是把同一个问题摊到十个文件里，反而多了 SW 清单和部署的麻烦。

### 三件小事（按性价比排序）

1. **维护「改动地图」**：`docs/CHANGE-MAP.md` 每个功能一栏——涉及哪些函数、必须同步哪几处、对应哪个 e2e。2 万行让人累的根源是「找不到、记不住」，地图直接解决这个；比拆文件管用。
2. **给同步点加守卫脚本**：版本号四处一致、提醒过滤三处一致、新字段三处齐全。约定靠人脑记必然漏，脚本 30 秒扫一遍，漏了报错。
3. **纯算法抽文件 + Node 单测**：即上面的例外，把最容易写错的部分单独关起来测。

---

## 4. 什么时候才真该拆

出现以下任一信号再重评：

- 单个文件超过 3 万行；
- 完成一个功能要同时改超过 5 个文件；
- 同一作用域的函数名冲突已经反复出现（v142 的 `ts-`/`tk-` 是前兆）；
- 要多人长期协作。

---

## 5. 一句话总结

**别跟行数较劲，跟「同步点」和「找不到的痛苦」较劲。** 拆文件解决不了后两者，地图和守卫脚本能。
