## 0. 结论摘要

1. **真正接通的服务端通知只有两条**：企业微信群机器人、邮件。所谓“浏览器提醒”是页面打开时由前端 `Notification` 接口发出的**本地通知**，不是 Web Push；关掉网页就不会响。
2. **账号级路由矩阵已经存在**：7 类提醒 × 2 个服务端渠道，存于 `app_settings` 的 `notify_prefs_<uid>`；默认用药 / 待办 / 倒数日 / 自定义 / 还款走企微＋邮件，习惯 / 每日小结只走企微。
3. **模块级与实例级渠道设置基本处于“存了但没用”状态**：喝水的 `notifyChannels`、478 的 `notifyChannels`、运动实例的 `notifyOn` + `channels` 都没有参与实际发送决策；运动的 `notifyScenes` 三个场景开关完全没有后端实现。
4. **前端本地通知与服务端通知口径不一致**：本地通知忽略 `notify=false`、忽略渠道勾选、忽略 `notifyScenes`，只覆盖用药 / 重复待办 / 逾期 / 习惯 / 喝水 / 运动 / 478 几类，且文案不同。
5. **推送预览不完整**：配置页“今日推送计划”只合并了当天提醒与每日小结，没有自定义通知、倒数日、还款提醒。（**v212 已修**：`push_preview` 已并入五源，展示迁至「通知路由」页）
6. **功能与类目不是一一对应**：喝水、运动、478 三个功能在服务端都归入 `habit` 一类；要做模块级路由，靠的是给排程条目补 `source` 来源标识，而不是新增后端类目。通知项按后果时效可分为紧急 / 当日 / 日常三级，排序规则见第 5 节。
7. **三渠道总控尚未落地**：浏览器 / 企微 / 邮件的独立开关与多选在模块 UI 有雏形但不生效，服务端渠道表只有企微与邮件，也没有统一全局开关；浏览器要成为真正的服务端渠道需要 Web Push。方案语义见第 8.7 节。

## 2. 三条路由的真实状态

### 2.1 浏览器提醒（本地通知，不是 Web Push）

- 实现位置：`index.html` 第 5018–5071 行的 `notifyPing()`，由每分钟一次的轮询驱动；使用 `Notification` 与 `ServiceWorkerRegistration.showNotification()`。
- 配置存储：浏览器 `localStorage` 的 `lifeboard.notify.on` / `lifeboard.notify.sent`；外加浏览器自身的通知权限。
- 生效范围：**只有页面开着时才可能触发**。没有订阅 token、没有 VAPID 密钥、没有服务端推送接口，关网页后不会收到任何消息。
- 限制：一次最多弹 3 条；按 key 当天去重；不读取账号级矩阵，不读取模块 / 实例渠道设置。
- 定位：应视为“当前页面的即时提示”，不应与服务端推送混为一谈。

### 2.2 企业微信群机器人

- 实现位置：`api/push.php` 第 180–220 行，发送群机器人文本消息。
- 配置存储：数据库 `users.push_webhook`、`users.push_enabled`。
- 限制：URL 只允许 `qyapi.weixin.qq.com/cgi-bin/webhook/send`；单条 2000 字节截断；机器人限每分钟 20 条。
- 测试消息：`明序 测试消息 / 时间是 … / 收到这条就说明推送通道是通的`，由 `api.php` 第 531–553 行触发。

### 2.3 邮件提醒

- 实现位置：`api/mailer.php` 第 483–493、563–576 行，经 `lb_mail_channel_sender()` 接入推送通道。
- 配置存储：`user_mail_config` 表，SMTP 授权码 AES-256-GCM 加密。
- 限制：收件人固定为账号邮箱，发件人必须与 SMTP 登录用户一致；站点邮箱只承担注册 / 找回密码，不用于提醒。

### 2.4 账号级矩阵、静默与每日小结

- 类别共 7 类：`med` 用药、`task` 待办、`habit` 习惯、`countdown` 倒数日、`notice` 自定义、`debt` 还款、`report` 每日小结，见 `api/push.php` 第 305–316 行的 `lb_notify_kinds()`。
- 渠道只有两个：`wecom` 企业微信、`mail` 邮件，见第 318–321 行的 `lb_notify_channels()`。**`browser` 不在服务端矩阵里**。
- 默认矩阵见第 323–333 行：全部默认双开，但 `habit` 与 `report` 默认只走企业微信（避免每天多发邮件）。
- 夜间静默：23:00–07:00，默认关闭；开启后命中静默时直接跳过，**不补发**（`api/push.php` 第 394–418、634–637 行）。
- 每日小结时刻可配，留空即不发（第 421–471 行）。
- 一轮推送在 `api/push.php` 第 645–715 行合并五路排程：当天提醒、每日小结、自定义通知、倒数日、还款提醒；去重键为 `日期|kind|id|时间` 加渠道维度。
- cron 入口为 `tools/push_tick.php`，**不能带 `--dry`**，否则不会真正发出。

## 3. 每个功能实际推送什么

> “服务端”指 `api/schedule.php` 排程后由企业微信 / 邮件发出的内容；“浏览器”指页面打开时本地通知的内容。两者**文案与过滤条件不同**。

| 功能 | 服务端排程 | 服务端文案 | 浏览器本地文案 | 关键过滤 |
| --- | --- | --- | --- | --- |
| 用药 | 每个药每个时段一条，`api/push.php` 第 503–545 行会把同一时刻多种药合并 | 单条：`该吃药了 / 药名 剂量单位（每天 HH:MM）`；合并：`该吃药了（N 种）` + 列表 | `N 次用药已过时间` 或 `N 次用药待服` | 按 9 点后、是否已记录判断 |
| 待办 | 仅当天到期，默认 09:00；可在任务上配 `notifyTime` | `该做这件事了 / 标题 + 时间块 + 备注 + notifyNote` | 重复任务过 `repeatTime` 才提示 `「标题」到时间了`；逾期单次任务合并为 `N 件待办已逾期` | 浏览器端不按 `notifyTime` 推当天待办 |
| 普通习惯 | 按 daily / weekly / monthly 与当天是否打卡过滤 | `icon 名称 / 今天还差 N 次` 或 `今天的习惯还没打卡` + `notifyNote` | 聚合为第一条：`「名称」还没打卡` | 浏览器不展示备注 |
| 喝水 | 按 `notifyMode` 生成多个时间点，`api/schedule.php` 第 256–275 行 | `该喝水了 · 今天还差 N 杯` / `今天还差最后一杯` | `喝水还差 N 杯，今天还没记` / `已 X 小时没记` | 浏览器不看 `notifyMode` 与时间点 |
| 运动 | 按每个运动实例的 `startTime` 与频率，`api/schedule.php` 第 279–340 行 | `icon 名称 / 该开始运动了`；当天已有记录则跳过。无实例时间时回退模块级 `今天还差 N 次` | 从模块适配成习惯：`「运动」还没打卡` | 浏览器不按实例、不看 `notifyOn` |
| 478 呼吸 | 每组一个点，最多 5 组，`api/schedule.php` 第 342–395 行 | `icon 478呼吸法 · 第 N 组 / 该做 478 呼吸了 · 今天还差 N 组` | `「478呼吸法」今天还差 N 组` | 任一提醒点已过且未达标即出现 |
| 戒烟 / 戒除 | **不排程、不推送**（`api/schedule.php` 第 177–180 行，模块 `quit` 不提醒） | 无 | 被 `isQuitLike()` 排除 | 明确不做 |
| 每日小结 | 默认 08:20 早报、12:30 午报、20:00 晚报，`api/schedule.php` 第 488–559 行 | 未完成数 / 逾期数 / 按 tag 分组；晚报为今日完成数 + 明日待办数 | 无 | 时刻可配，留空不发 |
| 自定义通知 | `api/schedule.php` 第 575–627 行，支持 once / daily / weekly / monthly | `🔔 自定义提醒 / 用户原文` | 无 | 按日期与重复规则 |
| 倒数日 | `api/schedule.php` 第 643–694 行，只对未来日期 | `📅 名称 / 还有 N 天或就是今天 · 目标日期 + 备注` | 无 | 过期不再提醒 |
| 还款提醒 | `api/schedule.php` 第 712–777 行；`money.notify.on` 默认关 | `💳 还款 · 债名 / 还有 N 天或就是今天 · 日期 + 还剩 ¥X + 最低 ¥Y` | 无 | 需主动开启 |
| 测试消息 | `api.php` 第 531–553 行；自定义通知“重发”借 `push_test.text` 原文再发 | `明序 测试消息 / 时间是 … / 收到这条就说明推送通道是通的` | 开启浏览器通知时立即验证一次当前待提醒项 | 仅手动触发 |

## 4. 功能接入通知类目对照

后端 `lb_notify_kinds()` 只定义 7 个类目。功能比类目多，因此**不能用类目区分喝水、运动、478**；建议保留 7 类不变，给排程条目补 `source` 字段做子类路由。

| 功能 | 现状后端类目 | 现状路由层级 | 建议来源标识 | 建议接入方式 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 用药 | `med` 用药提醒 | 账号级 | `med` | 已完整接入 | 同一时刻多种药合并后按 medications.id 去重 |
| 待办 | `task` 待办到点 | 账号级 | `task` | 已完整接入 | 支持任务级 `notifyTime` |
| 普通习惯 | `habit` 习惯提醒 | 账号级 | `habit` | 已完整接入 | 按日 / 周 / 月频率过滤 |
| 喝水 | `habit` 习惯提醒 | 账号级，模块渠道未用 | `water` | 保留 `habit` 大类，按 `source=water` 覆盖模块渠道 | 第一优先级缺口 |
| 运动 | `habit` 习惯提醒 | 账号级，实例开关未用 | `move` | 保留 `habit` 大类，按 `source=move` 与 `sportId` 覆盖实例渠道 | 需在三处排程同步 |
| 478 呼吸 | `habit` 习惯提醒 | 账号级，模块渠道未用 | `breathe` | 保留 `habit` 大类，按 `source=breathe` 覆盖模块渠道 | UI 已声明“仅作记录” |
| 戒烟 / 戒除 | 无 | 不接入 | `quit` | 明确排除，不排程、不推送 | 作为对照项验证路由不会误发 |
| 每日小结 | `report` 每日小结 | 账号级 | `report` | 已完整接入 | 默认只走企业微信 |
| 自定义通知 | `notice` 自定义提醒 | 账号级 | `notice` | 已完整接入 | 支持一次 / 每天 / 每周 / 每月 |
| 倒数日 | `countdown` 倒数日 | 账号级 | `countdown` | 已完整接入 | 只对未来日期排程 |
| 还款提醒 | `debt` 还款提醒 | 账号级 | `debt` | 已完整接入，默认关闭 | 需主动开启 `money.notify.on` |
| 测试消息 | 不排程 | 手动触发 | `test` | 不参与类目路由 | 仅用于验证通道连通 |

**分类决策**：不建议新增 `water` / `move` / `breathe` 三个后端类目。新增类目要同时改 `lb_notify_kinds()`、账号矩阵默认值、已有用户配置迁移和所有过滤分支，成本高且会打断现有用户设置；用 `source` 做子类覆盖，改动面小得多。

## 5. 通知项优先级排序分类

优先级按“错过的后果”与“时间窗口是否可补”划分，只影响排序与建议发送策略，不改变现有去重键。

| 级别 | 通知项 | 划分依据 | 建议发送策略 |
| --- | --- | --- | --- |
| 紧急 | 用药提醒、还款提醒 | 漏服有身体风险，逾期有实际损失，时间窗口不可补 | 企业微信 + 邮件双发；建议给这一级加夜间静默例外（需新增配置） |
| 当日 | 待办到点、自定义通知、倒数日、测试消息 | 当天有效，过期意义下降；倒数日按天只需一次 | 企业微信为主，邮件按账号矩阵；静默跳过不补发可接受 |
| 日常 | 普通习惯、喝水、运动、478 呼吸、每日小结 | 周期性节奏养成，单条遗漏可容忍，数量大 | 默认只走企业微信，邮件默认关；可合并汇总；模块渠道覆盖优先 |
| 不参与 | 戒烟 / 戒除 | 明确不推送 | 不生成任何排程 |

**排序规则**：紧急 → 当日 → 日常；同级按触发时间升序；同时间按通知类目顺序（用药、待办、习惯、倒数日、自定义、还款、每日小结）。不参与项固定排在末尾。预览页提供“按优先级 / 按触发时间 / 按通知类目”三种排序切换。

## 7. 已明确“没做完”的地方

1. **喝水**：`notifyChannels` 已存，但 `lb_push_tick_run()` 不读取；邮件 / 企微仍只看账号级矩阵（见喝水 P0 文档第 20–28 行）。
2. **478**：`breathe.notifyChannels` 已存，前端 UI 已明确写“勾选仅作记录、暂不单独生效”（`index.html` 第 8530–8539 行）。
3. **运动**：`api/schedule.php`、`api/ics.php`、前端 `buildICS()` 都不看 `notifyOn`；`notifyScenes` 三个开关没有后端实现（见运动 P0 文档第 21–37 行）。
4. **浏览器渠道缺位**：服务端 `lb_notify_channels()` 只有 `wecom` 与 `mail`，但模块 UI 给的选项是 `browser` / `wecom` / `mail`。
5. **本地与服务端口径冲突**：浏览器提醒忽略 `notify=false`、忽略渠道选择、忽略场景开关，且只覆盖部分功能。
6. **推送预览缺三路**：配置页“今日推送计划”只 merge 了当天提醒与每日小结（`api.php` 第 565–595 行），没有自定义通知、倒数日、还款提醒。

## 8. 建议实施方案

### 8.1 先定优先级语义

建议统一为：**实例 channels > 模块 notifyChannels > 账号级 notify_prefs**。浏览器单独定义为“本地页面通知”，不混进服务端 sender；模块 UI 里的 `browser` 选项需要重新解释或撤掉。

### 8.2 在排程条目上带来源信息

建议给每条排程加 `source`（如 `water` / `move` / `breathe` / `habit` / `med`）与 `sportId`，让 `lb_push_tick_run()` 在发送前解析渠道。现有去重键已经包含渠道维度，不必另造一套。

### 8.3 运动必须在三处同步

`notifyOn` 必须在前端 `buildICS()`、`api/ics.php` 的 `lb_ics_build()`、`api/schedule.php` 三处同步跳过；UID 与时间点要一起回归，否则订阅日历照推、服务端照发。

### 8.4 处理场景开关

`notifyScenes` 的三个场景（步数目标提醒 / 计划到点 / 每周周报）要么实现、要么从 UI 撤掉。保留假承诺会持续制造误解。

### 8.5 Web Push 是独立项目

若要求“关网页也能浏览器通知”，需要新增订阅 token、VAPID 密钥、服务端 push sender、订阅管理界面。建议与本次路由整改分开立项。

### 8.6 验收清单

1. 同一账号下设置“喝水只勾邮件、跑步只勾企微、478 关提醒”，断言服务端只发对应渠道。
2. `api/schedule.php`、`api/ics.php`、前端 `buildICS()` 产生的事件与 UID 集合一致。
3. 浏览器横幅不再绕开关闭开关。
4. 配置页“今日推送计划”补全五路排程。
5. 静默时段、去重键、每日小结时刻三项回归通过。

### 8.7 三渠道独立开关与全局总开关

产品设想是三种渠道（浏览器 / 企业微信 / 邮件）各自可独立开关、可多选，另有一个全局总开关一键控制全部。**交互上可以实现，但当前代码只实现了一部分**：

| 能力 | 当前代码状态 | 落地缺口 |
| --- | --- | --- |
| 单个渠道独立开关、多选 | 模块 / 实例 UI 有浏览器 / 企微 / 邮件三选勾选，但发送端不读取 | 让 `lb_push_tick_run()` 在发送前按层级解析渠道 |
| 账号级渠道选择 | 只有企微 / 邮件两列，`browser` 不在服务端渠道表里 | 要给浏览器明确定义：是本地通知，还是真正的 Web Push 渠道 |
| 全局总开关 | 只有企微的 `users.push_enabled` 与浏览器本地通知开关，没有统一三渠道总控 | 需新增账号级全局开关配置，并在发送前做总闸门过滤 |
| 浏览器作为服务端渠道 | 完全没有订阅 token、VAPID 密钥与服务端 push sender | 独立项目，不建议和本次路由整改合并 |

建议语义：**全局总开关是总闸门**，关闭后任何层级的勾选都不发送；单个渠道关闭只拦截该渠道，不影响另外两个；模块 / 实例渠道勾选仍按“实例 > 模块 > 账号”优先级解析。浏览器在现状下继续定义为“页面本地通知”，不计入服务端渠道表。

**渠道配置检测（预览页已模拟，产品落地需补）**：企微与邮件推送由用户先完成配置才能进行——企微要填机器人地址，邮件要配 SMTP 与授权码，浏览器要授予通知权限。运动弹窗已有 `moveChanState()` 做能力检测，但检测结果**只影响提示、不影响实际发送**；预览页已把它复刻成三渠道状态点与逐条反馈，并让未通过检测的渠道真正参与路由拦截。产品落地时应把同一份判定接入 `lb_push_tick_run()`：勾选渠道只是“想走这条路”，配置检测通过才真的发。

### 9.1 逐层完成度

### 9.3 P0 · 用户可感知的错误承诺

1. **关不掉的运动提醒**：`api/schedule.php` 的 `lb_schedule_day()`、`api/ics.php` 的 `lb_ics_build()`、前端 `buildICS()` 三处都只看 `startTime` / `freqKind` / `weekSel`，不看 `notifyOn`。实例弹窗明写“已关闭：不为这个运动发任何通知”，实际服务端照推、订阅日历照常生成事件。
2. **所有渠道勾选都是装饰**：`lb_push_tick_run()` 发送时只按账号级 `prefs[kind][channel]` 判断，排程条目里没有 `source` / `channels`。喝水只勾邮件、跑步只勾企微、清空某运动渠道，全部不影响实际发送。
3. **浏览器本地通知绕开所有关闭开关**：`remindItems()` 中普通习惯经 `assessmentHabits()` 进入，而 `activeHabits()` 不按 `notify` 过滤；喝水与 478 分支只看模块 `on !== false`（是否启用模块），不看 `notify`（是否开启提醒）；待办也不读 `t.notify`。服务端关掉了，浏览器还在催。
4. **渠道检测给假“服务正常”**：`moveChanState()` 的浏览器分支只查 `Notification.permission`，不查本地总开关；企微 / 邮件分支只查“配置存在”，但账号矩阵里习惯类邮件默认关闭，仍提示“邮件已配置，服务正常”。

### 9.4 P1 · 功能缺口与口径不一致

5. **三个场景开关是摆设**：`notifyScenes`（步数目标提醒 / 计划到点 / 每周达标周报）只有前端 `moveNotifyHtml()` 写入，没有任何后端实现。
6. **喝水 / 478 渠道无法全部取消**：`saveWaterNotify()` 与 `saveBreatheNotify()` 在空选时强制回退 `['browser']`，而 `saveMoveSportForm()` 允许运动实例存空数组，同一层级的“零渠道”语义不统一。
7. **推送预览缺三路**：配置页“今日推送计划”只合并当天提醒与每日小结，缺自定义通知、倒数日、还款。
8. **运动模块级渠道半吊子**：`moveSportModal()` 仍用 `m.notifyChannels` 作为新建运动的默认勾选，导致改模块渠道只影响新实例初始值、不影响推送。
9. **静默时段只管服务端**：浏览器本地通知在 9 点后照弹，没有静默概念。
10. **文档字段名偏差**：`docs/P0-运动模块通知路由.md` 写实例白名单字段为 `notifyChannels`，代码实际是 `channels`；`notifyChannels` 是**模块级**字段。实施时以代码为准（第 6 节已注明）。
11. **渠道 UI 覆盖不均**：用药、待办、普通习惯、自定义通知、倒数日、还款都没有渠道选项；用药连单条开关都没有，只能靠“已服药记录”抑制。

### 9.5 整改顺序建议

1. **先修“关不掉”**：三处 `notifyOn` 一次改齐，并让 `remindItems()` 过滤所有 `notify` 开关。改动小、收益最大，直接消除信任问题。
2. **再定路由语义**：给排程条目加 `source` / `sportId`，按“实例 > 模块 > 账号”解析；浏览器单列为本地渠道，不塞进 PHP sender。
3. **场景开关二选一**：要么实现三个场景，要么从 UI 撤掉，别继续留假承诺。
4. **统一空渠道语义**：喝水 / 478 与运动实例一致，允许“零渠道 + 提醒开关打开”的明确状态。
5. **补齐推送预览与渠道检测文案**：预览覆盖五路；检测文案改为“配置状态”，不要写“服务正常”。

### 10.1 文案模板与 HTML 邮件卡片（预览版）

**文案模板编辑器**跟随左侧“提醒场景”与数据项选择：选中哪一类，就编辑哪一类。默认模板刻意保留了“写死的那部分”——用药标题是 `该吃药了`，待办标题是 `该做这件事了`，正文则用 `{正文}` 占位，所以切换数据项时会自动带出该项的真实内容。可用变量为 `{标题}` `{正文}` `{浏览器文案}` `{功能}` `{类目}` `{场景}` `{时间}` `{来源}` `{优先级}`；点变量按钮可插入光标处，未提供的变量会原样保留，方便看出漏配。编辑框下方的「变量取值」区跟随当前场景或数据项变化：纯切场景时取该场景第一条示例数据的时间 / 来源 / 优先级，点某条数据则取该条的真实字段。取值**只读展示、不可编辑**，用户可编辑的是上方模板句式；产品落地时这层映射应由 `api/schedule.php` 从真实记录自动生成，不能让用户单独手填，否则会出现提醒内容与原始记录不一致。戒除类不排程，模板区自动禁用。

布局上把变量区从右侧整列挪到编辑框下方，压成横向紧凑卡片；右侧腾出的位置放「实时通知预览」，与编辑框共用同一份文案数据源，改模板不用往下翻就能看到服务端文案与浏览器文案，完整路由解析仍在页面下方。

**邮件 HTML 卡片**提供“纯文本（当前线上）/ HTML 卡片（建议）”切换，四种主题色与可编辑页脚。生成的卡片用**内联样式**，因为真实邮件不能依赖外部 `<style>`；页面右侧可直接查看源码。卡片只出现在邮件渠道的预览里，企业微信与浏览器文案不受影响。

这部分**只是方案模拟**，网站里要真正生效还差三块：

1. `api/schedule.php` 的 `lb_schedule_day()` 等排程函数目前把 `该吃药了` / `该做这件事了` / `今天的习惯还没打卡` 等句式写死在代码里。要支持模板，需先确定存储位置（账号级或场景级），再让排程生成时读取并渲染模板。
2. `api/mailer.php` 的 `lb_mail_send()` 当前把 `Content-Type` 固定为 `text/plain`；HTML 卡片要改成 `multipart/alternative`，同时保留纯文本兜底，并把卡片样式内联、对用户输入做转义。
3. 浏览器本地通知走 `remindItems()` 的独立文案，不共用服务端模板；若要三端一致，需要单独接一套。现有的 `notifyNote` 只是在固定正文后追加备注，不能替代模板。

### 10.2 板块总控（模块启用 + 通知矩阵合并视图）

预览页新增「板块总控」面板，把功能模块页的启用开关与设置页的通知通道矩阵合成一张 11 行表：每行一个板块，前两列是启用状态，后三列是企业微信 / 邮件 / 浏览器的渠道勾选。停药、停喝水等**板块停用**会连页面入口一起收起；**渠道留空**则功能照常用、只是不推送——两种诉求分开满足。批量按钮可一键全部启用 / 停用、全部渠道全开 / 留空。

同一面板承载两项原设置页能力：**免打扰时间段**改为全局设置，可改起止时刻（开始晚于结束即跨夜），并有「模拟当前」输入框当场看拦截效果；**每日小结三个时刻**可直接改，留空即不发，当前配置会显示在解析结果行。判定顺序为：全局总开关 → 免打扰 → 板块启用 → 渠道配置检测 → 板块渠道 → 实例 / 模块覆盖，任一层拦下即不再往下。现状模式下板块设置与现有模块渠道一样标注“存了不用”，切到目标模式才参与拦截。

## 11. 模块启用 / 停用 与 通知路由的合并方案（2026-11-27）

### 11.1 为什么必须合并

设置页的「功能模块」和「通知通道矩阵」现在在做同一件事的两遍：

| | 功能模块页 | 通知通道矩阵 |
|---|---|---|
| 用户看到 | 用药 / 喝水 / 运动 / 478 / 戒烟 的启用开关 | 用药 / 待办 / 习惯 / 倒数日 / 自定义 / 还款 / 小结 的渠道勾选 |
| 用户以为 | 停用 = 这个板块不提醒了 | 取消勾选 = 这类提醒不发了 |
| 实际存储 | `state.modules.<key>.on`；用药走 `state.modulePrefs.meds.on`（随全量快照同步） | `app_settings.notify_prefs_<uid>`（独立用户偏好） |
| 服务端读取 | **`api/schedule.php` 完全不读**，模块停用后照常排程 | `api/push.php` 的 `lb_notify_prefs_load()` 读取，决定企微 / 邮件 |

两套开关既不同源、也不同义，还会互相打架：模块停用了，提醒还在发；矩阵里两类都取消了，模块页仍显示"启用中"。合并不是省两个点击，而是消除矛盾承诺。

### 11.2 合并后的单一概念：板块

把"功能模块"和"通知类目"统一成**板块**，一个板块就是用户心里的"一件事"：

| 板块 | 对应旧模块 | 对应旧类目 | 停用后页面是否隐藏 |
|---|---|---|---|
| 用药 | `meds` | `med` | 是 |
| 喝水 | `water` | `habit`（子类 `water`） | 是 |
| 运动 | `move` | `habit`（子类 `move`） | 是 |
| 478 呼吸 | `breathe` | `habit`（子类 `breathe`） | 是 |
| 戒烟 | `quit` | 不推送 | 是 |
| 待办 | — | `task` | 否（待办是基础功能） |
| 普通习惯 | — | `habit` | 否 |
| 自定义提醒 | — | `notice` | 否 |
| 倒数日 | — | `countdown` | 否 |
| 还款提醒 | — | `debt` | 否 |
| 每日小结 | — | `report` | 否 |

每个板块只有两项设置：**是否启用** + **走哪些渠道**。功能模块页和通知路由管理页读写的是**同一份数据**，不再各存一套。

### 11.3 为什么"启用"和"渠道"仍然要分开

用户说"这两者其实是一样的"——在**效果**上确实一样（都能让提醒停下来），但不能合并成一个开关：

- 用户可能想**继续喝水打卡、但不要再被提醒**；合并成一个开关就只能"停用喝水"，连带页面入口、统计、连续天数全部藏起来。
- 所以：板块停用 = 功能和数据入口一起收起；板块启用但渠道留空 = 功能照常用、只是不推送。两种诉求都要保留。
- 单一数据源下的字段结构：`板块.{启用, 渠道:{浏览器, 企业微信, 邮件}}`；"渠道全空"是合法状态，不再强制回退到浏览器。

### 11.4 存储落地的两条路

**方案 A（推荐）：统一进全量快照的新顶层字段 `notifyBoards`。** 一次性把 11 个板块的启用与渠道写在一处，模块开关与通知矩阵都从它读写。因为项目的数据是全量快照，新增顶层字段必须同时改三处白名单：`normalizeState()` / `mergeStates()` / `repairBackup()`——只改前两处会在备份修复时把新字段抹掉（v78 事故）。迁移时从 `state.modules.<key>.on`、`state.modulePrefs.meds.on`、`app_settings.notify_prefs_<uid>` 读旧值填初始状态，旧字段保留一个版本只读兼容。

**方案 B（保守）：不新增顶层字段，前端做统一视图、保存时分写。** 有模块的板块继续写 `state.modules.<key>.on`，纯通知板块继续写 `app_settings.notify_prefs_<uid>`；路由管理页把两边渲染成一张表，保存时拆开回写。改动面小，但两处存储仍然可能不同步，只是把矛盾藏起来了。除非近期不动数据结构，否则不建议。

无论哪条路，服务端都要跟着改：`api/schedule.php` 的 `lb_schedule_day()` 与 `lb_schedule_reports()` 等排程入口先查板块启用，停用直接返回空；`api/push.php` 的 `lb_push_tick_run()` 发送前按板块渠道过滤，而不是只读 `notify_prefs_<uid>`。浏览器本地通知的 `remindItems()` 也要查同一份板块启用，否则"停用了还在弹"。

### 11.5 夜间静默 → 免打扰时间段（全局）

现状 `lb_notify_quiet_load()` 只存一个布尔，时段写死在 `lb_notify_in_quiet()` 的 `23:00–07:00`，用户不能改。建议存成 `{启用, 开始, 结束}` 三段，默认 `23:00 → 07:00`，支持跨夜（开始大于结束）。判定改为：全局开关启用且当前时刻落在区间内 → 跳过且不补发，口径不变；区间外照发。这个设置属于全局层，优先于所有板块与渠道，改名后要同步设置页文案、接口字段与后端函数注释。

### 11.6 每日小结自定义时刻

`lb_notify_report_load()` 已有 `morning` / `noon` / `evening` 三个时刻，空串表示该条不发，默认值 08:20 / 12:30 / 20:00。它现在埋在设置页底部，合并后应移到路由管理的「全局设置」里，与免打扰时间段放在一起。字段与接口都不用改，只挪位置；但要确保 `lb_schedule_reports()` 继续读取同一份值，避免"页面改了时间、推送没变"。

### 11.7 合并后的判定顺序

一次提醒能不能发出去，按下面的顺序判定，任一步拦下就不再往下：

1. **全局总开关**：关闭则全部不发送；
2. **免打扰时间段**：命中时段则跳过，不补发；
3. **板块启用**：停用则整块不排程、本地通知也不弹；
3. **渠道配置检测**：企微要填机器人地址、邮件要配 SMTP、浏览器要授予权限；未配置则拦掉该渠道；
4. **板块渠道**：只走板块勾选的渠道（浏览器单独按本地通知处理）；
5. **实例 / 模块覆盖**：运动实例开关与渠道仍按"实例 > 模块 > 板块"生效，但不再能突破上面任何一层。

### 11.8 v209 功能模块已落地，板块「启用」改为派生值（2026-11-27 补）

v209 已把功能模块页做成正式功能（`index.html` 的 `isModuleOn()` / `setModuleOn()`）：五个模块（meds / water / move / breathe / quit）可启停，停用 = 导航入口隐藏 + 锚点习惯归档（不计完成率）+ 提醒停止，数据原样保留。因此第 11 节方案要跟着收窄一条硬规则：

**模块类板块（用药 / 喝水 / 运动 / 478 / 戒烟）的「启用」不再是独立设置，一律派生自功能模块开关**：

- 通知路由页板块总控里，这五行的启用开关直接读 `isModuleOn()`，点击等同调 `setModuleOn()`；
- `notifyBoards`（无论方案 A / B）只为这五个板块存**渠道**，不存启用；基础板块（待办 / 习惯 / 自定义 / 倒数日 / 还款 / 小结）仍启用 + 渠道都存；
- 键名映射注意：功能模块键是 `meds`，板块 id 是 `med`，不要混用；
- 服务端排程要等效：`api/schedule.php` 生成这五类事件前也查同一开关语义（`modules.<key>.on === false` 或 `modulePrefs.meds.on === false` 即跳过），否则又是"前端藏了、后端照发"；
- 戒烟模块开着也永不推送（板块对照项不变）。

预览页已按此规则改造：板块总控顶部新增「功能模块开关 · 同步源」一排五个开关（默认对齐实测截图：已启用 1/5，仅戒烟），模块停用时板块行置灰、渠道锁定、路由判定直接拦截，并提示"导航隐藏、提醒停止，数据保留"。

预览页已按这个顺序接入：板块总控里改启用或渠道，右侧解析会当场显示"被哪一层拦下"。
