# P0 · 运动模块通知路由：实例级开关与渠道未落地

> 优先级：**P0（以后必做）**　创建：2026-11-26　相关版本：v195
> 定位：这是一笔明确的技术债 —— UI 已经做了、后端没跟上。用户勾了某个运动不接收提醒，**照样收到推送、照样进订阅日历**。
> 任何智能体接手本项目都应看到并安排重做。与 `P0-喝水模块通知渠道路由.md` 是同一类债，两笔要一起做。

## 一句话结论
运动页已上线「**每个运动单独开关提醒 + 单独选通知渠道**」的 UI 与数据存储，
但**实际推送与日历生成完全不读这些设置**——关掉某个运动的提醒后，到点照样推送、照样出现在订阅日历里；
给某个运动只勾邮件，实际还是按账号级「用户通知偏好」走。**UI 承诺与真实行为不一致，属于信任债。**

## 现状：做了一半的
- **UI 完整**：新建 / 编辑运动弹窗里有「到点通知你」开关与渠道多选（浏览器 / 企业微信群 / 邮件）；
  关掉时界面明写「已关闭：不为这个运动发任何通知」。
- **数据层完整**：`normalizeMoveSport` 已把 `notifyOn` / `notifyChannels` 收敛进白名单，
  保存、合并、导入、备份路径都会带上（v177 修过一次白名单漏登记）。
- **提醒时间点完整**：每个运动实例有自己的开始时间与频率（每天 / 每周几��），
  前端 `buildICS`、`api/ics.php`、`api/schedule.php` 三处都已按实例生成时间点，这部分与开关、渠道无关、已对齐。

## 没做的部分（真正的债）
### 一、实例级 `notifyOn` 三处都不读
- `api/schedule.php` 的运动分支：只读 `startTime` / `freqKind` / `weekSel` 生成提醒，**不看 `notifyOn`**。
- `api/ics.php` 的运动分支：同上，**不看 `notifyOn`**。
- 前端 `buildICS` 的运动分支：同上，**不看 `notifyOn`**。
- 结果：用户在某个运动上关掉「接收这个运动的提醒」，到点推送照发、订阅日历照常生成事件。

### 二、实例级渠道不参与路由
- `api/push.php` 的推送 tick：渠道来自**账号级**「用户通知偏好」（按 kind 给默认：习惯类默认企微）。
- 运动实例自己勾的 `notifyChannels`、模块级 `notifyChannels` **都没被读取**。
- 结果：给「跑步」只勾邮件、给「健走」只勾企微，做不到；清空某个运动的渠道也不影响实际发送。

### 三、三个「提醒场景」开关是摆设
- 运动提醒页有「步数目标提醒 / 计划类到点提醒 / 每周达标周报」三个勾选框，保存进了 `notifyScenes`。
- 但后端只有「按开始时间到点」一种提醒逻辑，**全项目搜 `notifyScenes` 只有前端的写入与 UI，没有任何后端实现**。
- 结果：三个勾选框怎么点都不影响行为。
- 处置建议：**要么实现、要么从 UI 撤掉**。其中「每周达标周报」需要一套全新的周报生成逻辑，成本不低；
  若近期不做，建议先撤掉这个勾选框，别留一个假的承诺。

## 造成的后果
- 用户关了某个运动的提醒，仍会在到点收到推送 —— 属于「关不掉」的信任问题，最容易被当成 bug。
- 订阅日历里出现用户已经明确不想要的运动事件，日历被污染。
- 「运动走邮件、喝水走企微」这种差异化提醒做不到。
- 三个场景勾选框让人以为能精细控制，实际上毫无作用。

## 为什么当时没做（缘由）
- v176/v184 落地重点是运动实例化（每个运动有自己的目标档、频率、记录方式、开始时间），
  开关与渠道是顺带落地的 UI + 存储，当时按「先存下来、路由后做」处理。
- 渠道路由要动 `api/push.php` 的推送 tick：让每条运动提醒在发送前读实例的 `channels` 并与
  账号级偏好叠加，涉及去重 key 与偏好的优先级语义，风险面大，不宜与一次 UI 改版混着提。
- 浏览器通知是前端 PWA（Web Push）路径，PHP 后端发不了；「浏览器」这一档在服务端路由里要单独处理，
  否则会与其他两档的语义不一致。
- 三处提醒生成（前端 `buildICS` / `api/ics.php` / `api/schedule.php`）必须**同时**改，
  只改一处就会出现「下载的日历有、订阅的没有」这类怪事 —— 这也是当时没敢顺手改的原因。

## 后续方向（重做时怎么做）
1. **`notifyOn` 三处对齐**：在「前端 `buildICS`」「`api/ics.php`」「`api/schedule.php`」的运动分支开头，
   统一跳过 `notifyOn === false` 的实例，与模块级 `m.notify` 的既有检查对齐。
   **三处必须一次改齐**，改完跑 `test-ics.php` + `test-schedule.php` + `verify-ics-subscribe.py`。
2. **渠道路由（实例级 > 模块级 > 账号级）**：建议语义 ——
   实例勾了某渠道 = 显式启用该渠道；实例没勾 = 回落到模块级 `notifyChannels`；模块也没配 = 回落到账号级偏好。
   浏览器渠道因为走 PWA，语义要单独说明（勾了只影响前端提醒，不产生服务端事件）。
   实现位置：`api/push.php` 的推送 tick，按提醒条目里的运动实例 id 反查实例渠道。
3. **三个场景开关**：短期建议撤掉 UI；要做的话，「每周达标周报」按周生成一条汇总（本周达标天数 / 总时长 / 总距离）。
4. **验收断言**：补一个 e2e —— 同一账号下「跑步关提醒、健走只勾邮件」时，
   断言 `api/schedule.php` 的当日排程里没有跑步、推送 tick 只发邮件不发企微；
   并且 `buildICS` 与 `api/ics.php` 生成的 UID 集合一致。
