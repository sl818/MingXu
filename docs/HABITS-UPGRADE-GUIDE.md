## 1. 一页结论

**做三件事，不做三件事。**

| 做 | 为什么 |
|---|---|
| ① 拆开「节奏」与「提醒频率」 | `notifyFreq` 目前同时承担「该不该做」和「何时提醒」，这是唯一的根本病灶 |
| ② 增加四种节奏：每天 / 指定周几 / 每周 N 次 / 每 N 天 | 现在只有「每天」，`本周 x/7` 把低频习惯永远压成不及格 |
| ③ 判定与展示按节奏分层 | 否则日历、周条、月报、连续天数会各自算出不同结论 |

| 不做 | 为什么 |
|---|---|
| 时段拆分（早/中/晚） | 呼吸模块已有 `groups` + `notifyTimes`，喝水已有分时段，再做就是两套 |
| 数值型计量（ml / 公里 / 分钟） | 运动模块已有 `sports` + `records` 全套字段 |
| 补卡 | 习惯「切历史日期打卡」已支持，运动有「补数据」 |
| 三步表单重构 | 收益低、回归面大；只需在现有表单插入一块「节奏」 |

**唯一待拍板**：你要的是「周一三五健身」这种**固定日**，还是「这周凑够 3 次」这种**弹性配额**？

- 固定日 → 照运动模块的 `weekSel` 抄，成本约完整方案的 30%，**不碰任何统计口径**；
- 弹性配额 → 才是真正的重构，必须连带改日历热力、周条、月报、连续天数四处。

本文按「两种都支持」写，但把弹性配额单独标为 **P1**，可以先只做固定日。

## 2. 现状事实（v205 核对）

### 2.1 判定链

`met(h, d)` 现在有 **五个分支**，顺序即优先级：

| 分支 | 判定 | 归属 |
|---|---|---|
| `h.med` | 当日排期数 > 0 且已服 ≥ 排期 | 用药（锚点） |
| `h.id === 'h_move'` | `moveMet(d)`，含老数据回退 | 运动模块 |
| `isSmoke(h)` | 当天没有「抽了」事件 | 戒烟模块 |
| `h.type === 'quit'` | v204 起：**必须主动打卡**才算守住 | 戒除 |
| 其余 `build` | `countOf(d, id) >= target` | 养成 |

**新模型只能作用于最后一个分支**，前四个一行都不能碰。

### 2.2 考核口径已统一

```
activeHabits(d)     = 纯习惯，已过滤 isModuleAnchor
moduleHabits()      = 四个模块（moduleAsHabit 生成的适配对象）
assessmentHabits(d) = 两者相加
dayStats(d)         = assessmentHabits + met()
```

`dayStats` 被日历页、今日页横幅、统计页共用。**任何新指标都必须挂在这条链上，不能另起第三套分母。**

### 2.3 判定只有一个出口：`habitDayMark`

```
future | fail | done | part | none
```

周条、本周计数、右上徽标全部只认它（v143 定下的规矩）。PRD 当年设计的「四函数」如果并排另造，会重现 v143 修过的「一张卡讲两套话」。

### 2.4 四处写死「7 天」

| 位置 | 现状 | 周期型进来后的冲突 |
|---|---|---|
| `habitWeekDone` | 循环 7 格数 `done` | 每周 3 次永远 3/7 |
| `habitWeekLabelled` | 7 格栅格 | 非要求日没有表达方式 |
| `habitMonthRow` | 按 `habitDueOn` 逐日算应打卡 | 应打卡仍取 `notifyFreq` |
| `streakOn` | 按天连续 | 周期型应按周期连续 |

### 2.5 提醒与节奏的耦合点

```
habitDueOn(h, d):
  const freq = h.notifyFreq;        // ← 病灶
  if (freq === 'weekly') return d.getDay() === h.notifyWeekday;
```

表单里「通知频率：每天/每周/每月」同时决定「多久提醒」和「多久该做」。**这是要拆的那一处。**

### 2.6 模块拆分带来的三个后果

| 后果 | 影响 |
|---|---|
| 常驻四项已不经过 `habitCard` | 改造习惯层几乎不会误伤模块，PRD 的 FR-12 风险大幅下降 |
| 模块层已各自实现配额/时段/多提醒 | 习惯层再做同类能力就是重复建设 |
| 考核口径已合并 | 习惯层新增指标必须与 `assessmentHabits` 对齐 |

### 2.7 数据层三个事实（与 PRD 写法不同，以此为准）

| 位置 | 实际行为 | 加 `sched` 要做的事 |
|---|---|---|
| `normalizeState` | 逐字段赋默认值，**不重建对象** | 需补 `sched` 的清洗与默认值，否则 `undefined` 会扩散 |
| `mergeStates` | habits 按 id 并集，**云端为主**，仅 `archivedAt` 取非空 | 新字段不需显式合并，但改节奏后可能被另一端旧快照覆盖（见 §8 RK-04） |
| `repairBackup` | `Object.assign({}, h, {...})`，**保留未知字段** | 结构不会丢；建议加结构校验，防止非法 `sched` 进库 |

> 注意：PRD 里写的「三处同步」对 habits **不是白名单重建**，因此不是「不改就丢数据」，而是「不改就出现未清洗的脏值」。性质不同，别按顶层字段的处置方式套。

## 4. 目标模型（最小版）

### 4.1 新增字段

只加一个对象字段，缺省即等于现状：

```js
h.sched = {
  kind: 'daily' | 'weekdays' | 'weekly' | 'interval',
  days: [0,2,4],        // weekdays：0=周日 … 6=周六（与全站一致）
  perWeek: 3,           // weekly：1..7
  intervalDays: 3,      // interval：2..60
  anchor: '2026-11-01'  // interval 的段起点，固定不动
}
```

约束：

- `kind` 缺省或非法时按 `'daily'` 处理 → **老数据零迁移、行为完全不变**；
- `interval` 必须用固定 `anchor` 分段（`floor((d - anchor) / N)`），**禁止**用「上次完成日」推算，否则拖延会让周期无限后移；
- 字段名刻意与运动模块的 `freqKind` / `weekSel` 语义对齐（不共用字段名，避免两模块互相污染）。

### 4.2 四种节奏的语义

| kind | 参数 | 今天该不该做 | 周期单位 |
|---|---|---|---|
| `daily` | — | 每天都该做 | 日 |
| `weekdays` | `days[]` | 只在选中的星期 | 日（非选中日 = 不需要） |
| `weekly` | `perWeek` | 本自然周未达成前每天可做 | 周（周一起） |
| `interval` | `intervalDays` + `anchor` | 本轮未完成前可做 | N 天滚动段 |

周起点统一取 `weekMonday`（周一），与 `habitWeekLabelled` 现有口径一致。

### 4.3 判定分层

| 函数 | 职责 | 是否新增 |
|---|---|---|
| `habitDueOn(h,d)` | 该不该做。**改为读 `sched`，不再读 `notifyFreq`** | 改 |
| `met(h,d)` | 日粒度达标。**语义不变**，只在 build 分支加「今天不属于要求日时返回 false」 | 改一处 |
| `habitDayMark(h,ds,d)` | 周条单格状态。**新增 `'off'` 态**表示「不需要做」 | 扩展 |
| `metPeriod(h,d)` | 本周期累计 vs 配额，返回 `{done, target, met, daysLeft}` | 新增 |
| `dayStats(d)` | **保持不变**，仍只统计日型习惯 | 不动 |

关键决策（与 PRD 不同，也是本指南最重要的取舍）：

> **周期型习惯不进入 `dayStats` 的分母。**
> PRD 原方案是「未达成前计入、达成后折叠」，会导致同一个习惯今天在分母里、明天不在，日完成率跳动，M3（三视图一致）几乎不可能守住。
> 改法：日型走 `dayStats`，周期型单独出「本周节奏」指标。代价是今日页有两个数字，收益是四处统计口径一处都不用改。

### 4.4 展示规则

| 位置 | daily | weekdays | weekly | interval |
|---|---|---|---|---|
| 卡片 pace 行 | `每天` | `周一/三/五` | `每周 3 次` | `每 3 天` |
| 卡片计数位 | `本周 x/7` | `本周 x/N`（N=选中天数） | `本周 x/N · 还差 M` | `本轮第 k 天 / 共 N 天` |
| 周条 7 格 | 现有三态 | 非选中日画 `off`（淡态 + 斜纹） | 同 daily，计数分母换 N | 改画本轮 N 格进度 |
| 连续 | `连续 N 天` | `连续 N 天`（只算选中日） | `连续 N 周` | `连续 N 轮` |
| 列表徽标 | `每天` | `周一三五` | `每周 3 次` | `每 3 天` |

单位必须随周期变。写「连续 12 天」而实际是按周算，是这次改造最容易出的错。

## 6. 兼容与迁移

| 场景 | 处理 |
|---|---|
| 老习惯（无 `sched`） | 一律按 `daily`，行为与现在完全一致 |
| 老习惯设了 `notifyFreq=weekly` | **不自动转成** `sched=weekly`。它当年只是「提醒频率」，转过去会改变判定语义，属于静默改口径 |
| 导出 → 导入 | `sched` 随对象整体带过（`Object.assign` 已保证） |
| 多端 | 同一习惯两端改节奏，云端覆盖本地（现有 `mergeStates` 行为）；改完在另一端刷新确认 |
| 回滚 | 旧版本不认 `sched`，按 daily 处理；数据不丢 |

## 7. 验收标准

**功能验收（精简 GWT）**

- Given 习惯 `sched={kind:'weekly', perWeek:3}`，When 本周已做 2 次，Then 卡片显示「本周 2/3 · 还差 1」，且不出现在「已达成」区。
- Given 同上，When 本周做到 3 次，Then 卡片进入「已完成」，本周节奏指标 +1。
- Given `sched={kind:'weekdays', days:[1,3,5]}`，When 周二，Then 该习惯不进今日待办，周条该格为 `off`（不需要做）而非空白。
- Given `sched={kind:'interval', intervalDays:3, anchor:'2026-11-01'}`，When 今天 11-07，Then 判定为第 3 段第 1 天，显示「本轮第 1 天 / 共 3 天」。
- Given 任何周期型习惯，When 查看今日页 KPI，Then 它不改变 `dayStats` 的分母（日型习惯数量不变）。

**三条一致性检查**

1. 同一习惯在今日页、日历、月报的结论一致；
2. 周条、徽标、「本周 x/N」三处数字一致；
3. 连续天数的单位与节奏匹配（日 / 周 / 轮），不出现「连续 N 天」配周型。

## 9. 分期

| 期 | 范围 | 门槛 |
|---|---|---|
| **P0** | 每天 / 周几 / 每周 N 次三种 + 节奏解耦 + 卡片与徽标文案 + 周条 `off` 态 | `verify-habit-sched` 全绿，全站回归无新增失败 |
| **P1** | `interval`（每 N 天）+ 明细页周期历史 + 暂停 | P0 上线两周无口径争议 |
| **P2** | 每月 N 次 / 每月某日 | 出现真实需求 |
| **不做** | 时段拆分、数值型、补卡、三步向导 | 已有模块承担 |

建议先做 P0 的**前一半**（只拆 `notifyFreq` + 固定周几），把「节奏」这条路走通，再决定要不要上弹性配额。这样即使中途放弃，也不会有半套模型留在代码里。

| Q4 | 改节奏后历史是否回算 | A 不回算 / B 回算 | **A**，并在保存时提示一次 |
